# Review — printed CODE128 fits 80mm paper (ut-docs#4403)

**Date:** 2026-10-15 · **Branch:** `fix/4403-escpos-code128-fit` · **Lane:** `lane:cloud-41`
**Author:** Sonnet dev subagent (complexity:easy) · **Reviewer:** independent Opus 5.5 subagent, fresh context

## What shipped

`internal/print/escpos.go`:

- `code128Data` builds the `GS k 73` payload with code sets B and C at the
  fewest CODE128 symbols (two-state DP; ties prefer B). A digit pair in set C
  is one byte 0–99; a literal `{` in set B is now escaped as `{{` (it was sent
  raw before, so a code holding `{` could be misread as a set switch).
- `barcodeModuleWidth` picks `GS w 2` when the symbol plus 10X quiet zones
  fits 576 dots (80mm), else `GS w 1`, else no barcode. The HRI line under
  the bars has to fit too (12 dots per font-A character, so at most 48
  characters).
- Width 1 sends `GS w 2` first. A printer that ignores n=1 (some Epson
  models document 2–6) then prints at 2 instead of `ESC @`'s 3.
- A code that doesn't fit falls back to text:
  - **Vouchers:** the existing wrapped-text branch.
  - **Labels:** the code is printed as clipped text.
  - **Receipt-number barcode:** skipped. The number is already in Meta.
- `RenderText` is unchanged.

A 13-digit code drops from 13 data symbols to 8. A 25-character lowercase
voucher code now prints at width 1 (660 dots at width 2 overflowed).

## Findings

| # | Severity | Finding | Outcome |
|---|---|---|---|
| M1 | minor | `GS w 1` is out of range on some Epson models, which then keep width 3 | **Fixed:** width 1 sends `GS w 2` then `GS w 1` (test `TestBarcodeWidthOneSetsTwoFirst`) |
| M2 | minor | A too-wide label code vanished from the label | **Fixed:** printed as text (test `TestRenderLabelTooWideCodePrintsText`) |
| m3 | minor | Codes of 49–60 digits fit as bars at width 1, but their HRI line (more than 576 dots) would be clipped | **Fixed:** the HRI width is part of the fit check, and the voucher falls back to text (49-digit case in `TestBarcodeModuleWidth`) |
| n1 | nit | A 1-dot module (0.125mm) is below some handheld scanners' minimum | Accepted. It is a last resort, the HRI text still prints, and a real-printer device check is pending |
| n2 | nit | `TestRenderBarcode`, `TestRenderLabel` and the voucher test build expected bytes with `code128Data` | Accepted. `TestCode128DataExactBytes`, a decode round-trip and the re-pinned sha256 cover the encoder independently |

## Verified

- **Encoder brute force (reviewer):** 200,000 random strings over `0123{a`,
  lengths 1–16, compared against an exhaustive search. Symbol count was
  minimal every time, the output decoded back to the input, and the emitted
  symbol count matched.
- **TDD re-verified in a detached worktree.** With the old `escpos.go`, the
  tests fail to compile. With stubs that keep the old behaviour, 6 tests fail.
  With the fix restored, they pass. The three review-fix tests failed before
  their fixes and pass after.
- **Byte change:** `TestRenderEmptyTrackingIsByteIdentical`'s `Render` hash
  was re-pinned on purpose. Receipt number `000000042` now encodes
  `{B0{C` plus 4 pairs. The `RenderText` hash is unchanged.
- **Gate:**
  - `gofmt`, `go build ./...`, `go vet ./...`, `golangci-lint` and
    `go test ./...` all pass.
  - Guards pass: data-access, i18n, core-neutral, deadcode-baseline-growth,
    netaccess, page-http-error, card-data-schema and compliance-claims.
  - `guard-deadcode-baseline` couldn't run in this container: the `deadcode`
    tool builds with go1.26 against the go1.27 module. CI runs it.
- **Not verified:** a real 80mm printer scanning a 25-character lowercase
  code (card acceptance). That needs hardware and is handed to a device
  check.

## Verdict

Safe to merge.
