# registers/locations: primary-only gate, then flip both tables to sync (ut-docs#1590)

**Card:** universaltill/ut-docs#1590 — the follow-up ut-docs#1584 filed on
itself. #1584 traced the decision that `registers` and `stock_locations`
had to stay per-till *because* `/registers` and `/locations` accepted
writes on a satellite; this card removes that reason and then flips both
tables to shop-wide sync.

**Verdict: safe to merge.** No blocking issues. One Medium finding
(upgrade-path consequence, accepted with a recommended follow-up card) and

### 2. The FK ordering claim, proven rather than argued

Traced first, then falsified. `registers.location_id` FKs
`stock_locations(id)` (`internal/db/migrations/001_init.sql:86`).
`ApplyAdmin` phase 1 walks `adminTables` in **reverse** (deletes) and
phase 2 **forward** (upserts), so with `stock_locations` before
`registers`:

- phase 1 prunes `registers` before `stock_locations` — a location is
  never deleted while a register still points at it;
- phase 2 upserts `stock_locations` before `registers` — a register's
  `location_id` target always exists by the time the register lands.

Neither direction can violate the FK. Two secondary cases also hold: a
register the primary's bundle *keeps* can never reference a location the
bundle omits (the primary's own DB has FK integrity, so the location is in
the bundle too); and a register that phase 1 *retires in place* keeps its
`location_id`, which merely FK-blocks that location's own delete a moment
later and pushes it onto the same retire-in-place path — handled, not an
error.

Empirically confirmed by deliberately swapping the two entries and
re-running the data tests:

```
=== RUN   TestAdminDumpApplyRoundTrip_RegistersAndStockLocations
    sync_admin_repo_test.go:994: apply: apply registers: constraint failed: FOREIGN KEY constraint failed (787)
--- FAIL: TestAdminDumpApplyRoundTrip_RegistersAndStockLocations (0.06s)
```

So the ordering is both correct and actually guarded by the new test.
Order restored; `git status` clean.

`registers` and `stock_locations` are also the *only* FK pair among the
synced tables: the schema's other referrers (`inventory`, `sales`,
`shifts`, `stock_movements`) are all deliberately outside `adminTables`,
so no further ordering constraint exists in either phase.

### 3. Gate placement and coverage

`requireManager` runs first, `requirePrimary` second, on all six mutating
handlers — permission before topology, never the reverse, never skipped.
Both `GET /registers` and `GET /locations` are **not** gated, so a replica
can still read both pages (correct — the gate is about writes).

No handler on either page is missing the gate: each page has exactly one
GET and three POSTs, and all three POSTs carry it.

Every *other* write path into these two tables was checked by grep and is
already primary-only or non-user-facing:

- `POSRepo.CreateRegisterForEnrolment` — called only from
  `POST /api/sync/enroll`, which returns 409 on a replica
  (`internal/pages/sync_api.go:340`).
- `POSRepo.EnsureRegister` / `EnsureMainLocation` — self-heal-only, fire
  only when zero (active) rows exist, not operator-facing admin writes.
- No other callers of `CreateRegister`, `RenameRegister`,
  `SetRegisterLocation`, `SetRegisterActive`, `CreateStockLocation`,
  `RenameStockLocation`, `SetStockLocationActive` exist outside the two
  gated pages.

Separately confirmed the gate does **not** over-reach: choosing which of
the shop's registers a till *is* stays available on a replica, because
that is a per-till settings key (`sync.till_register_id`,
`PerTillSettingPrefixes`-protected) written from `settings_page.go`, not a
`registers`-table mutation.

### 4. Retire-in-place / UNIQUE mangle

Both tables declare `name TEXT NOT NULL UNIQUE`, so `unique: ["name"]` is
required, not decorative. On an FK-blocked prune `deleteMissing` sets
`is_active = 0` and rewrites `name` to `name || '~' || id`, guarded by a
`CASE … LIKE '%~' || id` that keeps it idempotent across pulls. That
releases the name *in phase 1*, before phase 2 upserts the primary's row,
so the UNIQUE-violation deadlock the field exists to prevent cannot form.
Both new retire-in-place tests exercise the real FK block (`shifts` for
registers, `inventory` for stock locations) with
`PRAGMA foreign_keys = ON` genuinely in effect (`internal/db/db.go:68,89`
plus the tests' own migrated DBs) — they fail loudly, not vacuously, if
the fallback stops working.

Zero-active-rows on a replica is also structurally impossible: the
primary's own last-active-register / last-active-location guards keep it
at ≥1 active row, and those rows upsert onto the replica as active.

## Findings

### Medium — no upgrade-path note for shops that already have satellite-local registers/stock_locations *(accepted; follow-up recommended)*

Nothing in the application ever hard-deletes either table (verified: no
`DELETE FROM registers` / `DELETE FROM stock_locations` anywhere outside
`deleteMissing`; both pages only soft-deactivate). So for these two tables
`deleteMissing` can only ever fire against **pre-existing divergence** —
rows a manager created on a satellite under the old, ungated behaviour
this card removes.

On the first admin pull after upgrading, such a row is either hard-deleted
with **no log line at all** (it has no history to FK-block it), or
retired-in-place with a mangled name (it does). Concretely:

- a satellite-local stock location holding real inventory becomes
  `is_active = 0` and named `Back Room~<uuid>`, so that stock silently
  drops out of every active-location picker while its `inventory` rows
  survive underneath;
- a satellite-local register with shift history is deactivated, which
  makes that till's `sync.till_register_id` stale;
  `pos.ResolveTillRegisterID` then falls through to re-resolution and
  returns `ErrRegisterIdentityAmbiguous` whenever the primary has ≥2
  active registers, so shift/payout write paths fail **loudly** until a
  manager re-picks in Settings → Tills.

This is the intended "primary wins" semantic, the failure mode is loud and
recoverable rather than silent corruption, and preventing all *future*
occurrences is the entire point of the card — so it is not a merge
blocker. But the diff ships no release note, no manual sentence and no log
line for that one-time reconciliation. **Recommend a follow-up card**: at
minimum a `logging.L().Warnf` in `deleteMissing` when it prunes a
`registers` / `stock_locations` row (today it logs only when it *cannot*
prune), and a line in the release notes / `multitill.md` for shops
upgrading a multi-till setup.

### Minor (UX) — no replica banner on `/registers` and `/locations`

operator only finds out after submitting. `/inventory`
(`inventory_page.go:104` → `inventory.html:7`) and the catalog page
already pass `SyncPrimary` into the template and render
`sync.banner_replica` plus an "open on the primary" link — that is the
established pattern for exactly this situation. The card's acceptance
criteria are the gate plus a clear localized message, both delivered, so
this is not blocking, and it plausibly belongs to ut-docs#1585's broader
replica-write sweep rather than here. Flagging so it is a decision rather
than an oversight.
