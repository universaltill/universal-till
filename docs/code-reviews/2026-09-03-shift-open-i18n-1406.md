# Code review: shift-open HTML fragment i18n (ut-docs#1406)

**Date:** 2026-09-03
**Author:** autonomous pipeline (`lane:cloud-54`), Dev at Sonnet (complexity:easy)
**Reviewer:** independent fresh-context Sonnet subagent, worktree-isolated
**Repo / PR:** `universal-till`, branch `fix/1406-shift-open-i18n`

## What shipped

`internal/pages/shifts_api.go`'s `respondShiftSuccess` — the HTML-fragment
path of `POST /api/shifts/open` — hardcoded untranslated, unescaped English
prose:

```go
writeHTML(w, http.StatusOK, fmt.Sprintf("<div class='success'>Shift opened: %s</div>", data.ShiftID))
```

Same defect class ut-docs#1289 already fixed on the sibling
`respondCloseSuccess` function in the same file (invisible to
`guard-i18n.sh` because it's a `fmt.Sprintf` literal inside Go code, not
template markup).

Fix follows the `respondCloseSuccess` precedent exactly:
`httpx.ResolveLocale` → `httpx.T(locale, "shifts.open_success")` →
`fmt.Sprintf` → `html.EscapeString` → `writeHTML`. New key
`shifts.open_success` (`"Shift opened: %s"` in en) added to all four
`web/locales/*.json` files (en, ar, fa, tr), alphabetically placed between
`open_since` and `opened_at`.

`data.ShiftID` is `uuid.NewString()`, never user input — not currently a
security issue, but the escape keeps this function consistent with its
sibling.

### Findings (both non-blocking)

1. **nit — fixed.** The English-locale assertion in the new test
   (`strings.Contains(body, "Shift opened:")`) is not actually
   discriminating: `en.json`'s value is textually identical to the old
   hardcoded literal, so it would pass unchanged against the pre-fix code.
   The real regression proof is the `fa`-locale assertion, independently
   confirmed to fail pre-fix. **Action:** reworded the comment above the
   English check to say plainly it's a rendering sanity check, not proof
   of the fix, and pointed at the fa assertion as the actual regression
   guard. No behavior change.
2. **nit, pre-existing, out of scope — filed as ut-docs#1504.**
   `respondAdjustmentSuccess`, one function below in the same file, has the
   identical defect (hardcoded, untranslated, unescaped), also invisible to
   `guard-i18n.sh`'s regex (which doesn't match a literal buried inside
   `fmt.Sprintf(...)` passed to `writeHTML`). Correctly out of #1406's
   stated scope; filed separately with a note suggesting the guard's regex
   itself may need widening so this class stops recurring silently.

No blockers. No file-write/`MkdirAll` or cwd-relative-path issues (pure
in-memory string formatting, no I/O).
