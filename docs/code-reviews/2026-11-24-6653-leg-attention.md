## What shipped

- `GET /ui/settings/payment-attention`: a "Payments needing attention" card, lazy-loaded after `#settings-payments`.
  - It lists legs whose newest journal row is `reverse_failed` or `warned`.
  - It is shown to managers only (`refund` permission). Cashiers get an empty fragment.
  - It is hidden when the list is empty.
- `POST /api/pay/legs/retry` (only for `reverse_failed`):
  - `BeginRetry` appends `reversing` in one transaction and refuses every other state.
  - The counter n = the number of `reversing` rows, so the first Retry is `:2`.
  - The reversal is sent as broker key `refund:reversal:<id>:<n>` plus event id `reversal:<id>:<n>` (F2).
  - The outcome is appended as `reversed` or `reverse_failed` and audited.
  - It fails closed: no `reversing` row means nothing is sent.
  - It uses the shared tap in-flight guard and a detached context.
  - No refund plugin installed counts as a failure (F3).
- `POST /api/pay/legs/resolve` (`warned` or `reverse_failed` → `resolved`): an optional audit-only note, capped at 200 characters.
- Both POSTs need the `refund` permission and a fresh step-up PIN. Both are denied in demo; the read-only GET is allowed there.
- `GET /api/pay/attempts/attention` gains the additive fields `legs` and `legs_count`.
- F1: on an additional till, a refused tap reversal now writes `reversing` then `reverse_failed` (`main_till_only`). Before,
  it tried `captured`→`reverse_failed`, which the journal refuses, and the leg was never listed.
- The live reversal key stays `:1` (F4), pinned by `TestReversal_LiveSendKeyStaysOne`.
- #6908 (failed reversal from `tapUnlock`): `TestTapUnlockFailedReversalIsListed_6908` proves such a leg is now listed and can be retried.

## Findings (Fable review)

| # | Severity | Finding | Outcome |
|---|---|---|---|
| S1 | should-fix | Resolve copied the old row's `At`, so the retention sweep could delete a chain resolved today | fixed: `At` zeroed, test red→green (re-verified by the orchestrator) |
| S2 | should-fix | An unknown tap at restart sits in both `payment_attempts` and the journal. Settling it in one leaves it open in the other (a stale "Please check" row, or the tap gate still refusing) | deferred → ut-docs#7025; it changes tap gate semantics and needs an Architect call |
| S3 | should-fix | Demo denied the lazy GET, so Settings showed an orphan refusal | fixed: GET allowed in demo, POSTs denied, route classification test updated |
| N1 | nit | `legRefTail` sliced bytes | fixed: rune-safe, `TestLegRefTail_RuneSafe` |
| N2 | nit | the note allows U+2028 and bidi characters | accepted: audit-only and escaped |
| N3 | nit | the list is capped at 100 with no "more" sign | accepted: a till with 100 unsettled legs has a bigger problem; revisit if seen |
| N4 | nit (ut-docs) | the contract said the event id is about 65 characters | fixed |
| O1 | risk | A Retry after a first send that really refunded relies on the provider refusing an over-refund (the key is new by ADR design) | accepted: always the full capture; the card, PIN dialog and help say to check the provider first |

The reviewer found no double-refund path that the design does not already bound:
- concurrent Retries, and Retry against Resolve, are serialised by the guard plus the `BeginRetry` transaction;
- boot reconcile touches only rows older than process start and never `reverse_failed`;
- keys cannot collide with the live `:1` or with client refund ids.
