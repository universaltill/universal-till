# 2026-09-27 — Idle auto-lock looped instead of locking (ut-docs#3005)

## What shipped
- **`auth.Service.IdleLock(ctx, token)`.** Revokes the caller's session and fires the existing `idle_lock` audit. An empty, unknown or already-revoked token is a no-op.
- **`POST /api/auth/idle-lock`.** Middleware-exempt under `/api/auth/`, like logout. It calls `IdleLock`, clears the cookie and answers 204. GET is not routed. The route is on the demo-mode allow-list.
- **The `app.js` idle timer** fires once, POSTs that endpoint with `keepalive`, then goes to `/login` whatever the POST answers.
- **Comments updated:** "cosmetic client timer" wording in `service.go`, `init.go` and `app.js`.
- **Why:** the owner saw a whole-screen refresh every 10 minutes on the tablet. Logcat showed `idle-lock` reloads all night, and a screen recording showed the sale screen rebuilt and the keypad never shown. The client timer counts from input or page load; the server clock is moved by any touching request, so after a page load it trails. `GET /login` then saw the session as fresh, bounced to `/`, and the page reloaded, forever. #2901 fixed only the case where the last event was a touch.

## Review
Independent reviewer: Fable 5.1. The fix was written by Opus 5.5. **Safe to merge.**
- **CSRF:** the cookie is `SameSite=Lax`, so a cross-site POST carries no cookie (the Lax+POST exception does not apply to an explicit SameSite). GET is refused.
- **Plugin pages** are sandboxed iframes with no scripts or forms, so a plugin cannot trigger this.
- **Blast radius:** revocation is by token hash, so another operator's session survives. The kiosk page doesn't load `app.js`. With the lock set to 0 there is no timer.
- **TDD re-verified by the reviewer:** reverting the service or the handler makes both Go tests fail meaningfully (build error / 404).
