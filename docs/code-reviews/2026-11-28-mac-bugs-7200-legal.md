# Legal review: cloud-backup privacy note and key status (ut-docs#7200, #7199)

Independent pass: a real Fable subagent ran the counsel review (2026-11-28,
`legal/SKILL.md` s6; the Skill tool does not list `legal`, so the role file
was read directly). Drafter was Sonnet 5.5, so the reviewer is on a different
model. Its verdict is the last section; the first-draft self-check is kept
above it. Owner sign-off is still pending.

## Scope
`backup.cloud.privacy`, `backup.cloud.key.status_off`, the Cloud backups card
(`web/ui/partials/backup_cloud_card.html`), the choice handler
(`internal/pages/offsite_backup_api.go`) and the uploader escrow code.

## Facts (what the code does)
| Fact | Source |
|---|---|
| Choice `""`/`on`/`off` in `backup.offsite.key_in_cloud`; uploads run in every state | ADR-0199 D17, `uploader.go` |
| On sends the wrapped key; Off only stops sending | `uploader.go` register/syncEscrow/ApplyKeyChoice |

| The old Off status said "only on this till and in the copy you save" with no check of the cloud | old `status_off` |

## Findings, ranked
1. **High, likely: false statement about what we hold after No.** The privacy note asserted a held wrapped copy to owners who chose No and never had one. Over-claiming exposure is the safe side legally but misleads the owner about their own data and their choice (UK GDPR Art. 5(1)(a) transparency, Art. 13; unverified section pinpoints). Fixed: the wrapped-copy sentence is its own key `backup.cloud.privacy_copy`, shown only when the choice is On or a copy is held, and not when the owner blocked it.
2. **High, plausible: false "only on this till" after On then Off.** Off does not delete a held copy, so the claim was untrue and the owner could believe a decryptable copy was gone. Fixed: new setting `backup.offsite.copy_held` (cloud's last `key_in_cloud` answer, or the till's own successful send; set provisionally on On->Off when the cloud cannot be asked). `status_off` now says only what is certain ("This till does not send a copy"); `status_off_held` says the cloud still holds the copy and that only the owner can delete it on my.universaltill.com. Both keys are `review: legal`/`standard` in `en.meta.json` (held and privacy ones legal).
3. **Medium: behaviour vs. text, delete on Off.** Security-first would delete the held copy when the owner says No. Not done: ADR-0199 D17 (binding, ADR-0007) says a till token has no right to drop the copy (least privilege), and ut-cloud has no device delete route. Doing it needs a superseding ADR and a cloud route. Decision: keep behaviour, make the text honest, tell the owner the real way to delete. Owner question below.
4. **Low:** `privacy` also claimed "key release need a fresh sign-in"; reworded to restore approval, which is always true. "Anyone who gets into your account could approve a restore and a key release" moved into the conditional sentence (a key release exists only with a held copy).

## Owner questions
1. Should Off delete the held cloud copy, via a new ut-cloud device route guarded by the PIN step-up on the till and an owner email? Recommendation: no for now. The cloud copy is irreversible to lose when the till is lost too, so a deliberate owner step on my. (D17) is the right gate; the new text points to it.
2. Run the Fable counsel pass on the new wording before release (recommended; it is legal text).

**Law (unverified pinpoints).** The shop is controller and we are processor, so
UK GDPR Art. 13 is owed by the shop; our duties here are Art. 28(3)(a) and
Art. 29 (act on the controller's instruction). A "No" described as "only on this
till" while we keep a wrapped key is the exposure in F1/F2. Art. 5(1)(a) and
12(1) apply to what we tell the owner by analogy. Art. 25(2): the default is
undecided with no copy sent, which fits. Art. 32(1)(a): keeping the copy after
Off is defensible only because it is disclosed and the owner can delete it.
Misrepresentation Act 1967 s.2 and DE UWG s.5 for a misstatement to a business
customer. Effect of the Data (Use and Access) Act 2025: not checked.

**Is "Off never deletes" disclosed?** Yes after On -> Off (`status_off_held`,
`privacy_copy`, the PIN summary). Not at the first choice after a restore or a
link (F1, now fixed) and not after an offline Off (F2, now fixed). The 14-day
and database-backup lingering of a deleted copy belongs in the privacy notice
(ADR-0199 s11.2); not checked here.

**Redrafts applied** (English only, other locales come from Weblate):
- R1 `backup.cloud.key.ask_off_text`: "If no: this till does not send a copy of your backup key to the cloud. If the cloud already holds a copy, it stays there until the shop owner deletes it on my.universaltill.com. With no cloud copy, only this till and the copy you save hold the key; if you lose both, nobody can read your backups, including us."
- R1 `backup.cloud.key.choose_off`: "No, do not send a copy"
- R2 `backup.cloud.key.blocked`: "The shop owner switched off the cloud copy of your backup key on my.universaltill.com. Backups still go to the cloud, encrypted with the key on this till."
- R4 `backup.cloud.state_not_in_plan`: "Cloud backups are not part of this shop's plan. New backups stay on this till."

Metadata descriptions of the changed `review: legal` keys updated in
