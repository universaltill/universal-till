# Review: personal display part 2/3, render call sites use the session-aware resolver (ut-docs#3438)

**What shipped:** every per-viewer page render in `internal/pages` (52 files, 61 sites) now reads `d.ResolvedTheme(r)` instead of `d.CurrentState().Theme`. That includes the `/ui/theme-sync` poll (`themes.go`), the plugin page iframe (`plugin_page.go`), `/tills` (`sync_api.go`) and two indirect `st.Theme` sites the card's grep missed (`country_settings_page.go`, `settings_page.go`). The sale screen's browsing mode (`buttons_api.go`) becomes `common.ClampBrowsingMode(d.ResolvedBrowsingMode(r))`. The card said to drop the clamp, but the resolver returns the till value unclamped when no personal value applies, and `TestButtonsUIFragment_DefaultBrowsingModeIsCategoryTiles` fails without it. The settings page keeps a separate `tillTheme` so the till theme picker (`settings.html`) still preselects the till value while the page itself wears the viewer's theme. Five `deadcode-baseline.txt` lines (resolver + `NewUserDisplayRepo`/`UserDisplayRepo.Get`) are removed because they are now reachable. The docs-shots manifest `surface_sha256` was refreshed: the driven run shows no-override HTML is byte-identical to `main`, so no screenshot changes. Excluded on purpose: the httpx error path (`InitTheme`/`RenderError`, no `Deps`), the cloud check-in `DeviceExtra` payload (no viewer), the settings browsing-mode picker, and setting writes.

No role holds `personal_display` today (migration 061 registered it without grants; #3440 grants it), so nothing changes for any user until #3440 ships. No ADR (follows #3149's design), no i18n, no migration, no help change.

Sonnet built it. Independent reviewer: Opus 5.5 subagent. Tester: separate subagent.

## Findings
1. **Medium (only after #3440), deferred to #3440.** Error pages render the till theme server-side (`internal/httpx/render_error.go:79`), but `base.html`'s theme-sync poll now returns the personal theme, so for a manager with a personal theme an error page flashes from till to personal theme, and boosted navigation between an error page and a normal page becomes a full load. `TestPersonalDisplay3438_ExclusionsKeepTillTheme` checks server HTML only. Fix belongs with the feature that makes a personal theme reachable: a theme-resolver hook in httpx so error pages use the viewer's theme. Recorded on #3440.
2. **Low, fixed.** `TestPersonalDisplay3438_SellScreenPersonalBrowsingMode` only asserted the category-tiles marker was absent, so an empty or error fragment would pass. Now it also requires `class="products-strip"`.
3. **Low, fixed.** The source guard matched only the literal `CurrentState().Theme`, so the indirect `"theme": st.Theme` sites could regress unseen. Added a `"theme":\s*\w+\.Theme` regex check. Mutation: reverting `country_settings_page.go:201` to `st.Theme` turns `TestNoRenderSiteReadsTillThemeDirectly` red; restored, green.
4. **Very low, accepted.** The exclusions test resets `httpx.InitTheme` to `""` rather than the prior value; the test is in package `pages` and cannot read the private value, `""` is the package default, and every other test that needs a theme sets it itself.
5. **Notes for #3440 (recorded there).** After saving a till theme, Settings still wears the manager's personal theme, so the save may look ineffective; the kitchen display and `/orders` follow whoever is signed in; a saved personal theme is used as-is, so #3440 must validate on save and fall back when the theme plugin is gone; with `UT_AUTH=off` any personal row applies (existing behaviour).
- Checked, no defect: missed sites (none); sale-screen cache keys include browsing mode and the cached fragment never reads the theme, so no cross-user leakage; self-order kiosk and order-tracking pages are auth-exempt standalone pages with no theme-sync poll, so a staff theme cannot reach them; per-request cost is one permission check (per-request snapshot) plus one indexed lookup only when granted.
