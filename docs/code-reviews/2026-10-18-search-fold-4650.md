# Review: one locale-aware search fold for vouchers, customers and the item search (ut-docs#4650)

Date: 2026-10-18 · Branch `fix/4650-search-fold` · Card complexity: medium
Built by the lane:cloud-41 session (Opus 5.5, inline Dev). The planned Fable review was refused (the account was out of Fable credits, HTTP 429), so the independent review fell back to a fresh-context Sonnet subagent (MODEL-ROUTING's fallback).

## What shipped
- `internal/data/search_fold.go`: `SearchFold`, the one key the till's text searches match on.
  - It trims the text. ASCII text takes a fast path (`strings.ToLower`).
  - Otherwise it NFC-normalises, but only when the text isn't NFC already, so an NFD paste meets stored NFC text.
  - It then folds rune by rune as `lower(upper(r))`, plus ß/ẞ→ss. That sends final ς to σ and Turkish I/ı/İ/i all to i. A decomposed `i`+U+0307 also folds to i.
  - It is locale-independent on purpose: every till treats the four i letters as one in search. That only widens matches, and no locale has to reach the repository layer.
  - Accents are kept, so "Muller" does not find "Müller".
  - `FoldItemName` is unchanged. It is an exact-match key, and the counter-order conversion refuses ambiguous names, so widening it would change which names collide.
- The same function is registered once, in package `init`, as a deterministic SQLite scalar function `ut_search_fold`, through modernc's `MustRegisterDeterministicScalarFunction`.
- `POSRepo.SearchItemsForShortcuts` (the sell screen's live search and the Designer's add-shortcut search) and `POSRepo.SearchCustomers` (the data-management customer picker) match the name with `instr(ut_search_fold(name), ?) > 0`, using the query folded in Go.
  - `ORDER BY`, `LIMIT` and `OFFSET` stay in SQL.
  - SKU, barcode, phone and email keep their `LIKE`.
- `POSRepo.ListVouchers` folds with `SearchFold` instead of `strings.ToLower`.
- Tests in `internal/data/search_fold_test.go`:
  - `TestSearchFold`
  - `TestSearchItemsForShortcuts_UnicodeFold` (with an empty-query case)
  - `TestSearchCustomers_UnicodeFold`
  - `TestListVouchers_LocaleFold`
  - `BenchmarkSearchItemsForShortcuts10k` (ascii / turkish)

## Measurement (card AC: 10k items, Go-side scan vs SQL function)
`BenchmarkSearchItemsForShortcuts10k`, 4-core cloud container, 20-row page:

| catalogue | before (`LIKE`) | first cut (`x/text/cases`) | shipped |
|---|---|---|---|
| ASCII names | 11.8 ms | — | ~16 ms |
| all-Turkish names (every row on the slow path) | 9.5 ms | 53 ms | ~20–22 ms |

The first cut used `x/text/cases.Fold` with an NFD round trip. That cost 3.4 µs and 12 allocations per row. The rune loop with an NFC quick check costs under 1 µs and 2 allocations. The rest of the overhead is the driver's per-row callback.

The SQL function was kept over a Go-side scan. A Go scan would move all 10k rows, with their barcode sub-select and image join, through `database/sql` to page in Go. The old `%…%` LIKE was never indexable either.

## Findings
Independent review (Sonnet): safe to merge, no blockers or majors.
- **Minor, fixed.** A decomposed `i`+U+0307 typed in the query didn't meet a stored "İzmir", because NFC has no precomposed form for it. It now folds to i. `TestSearchFold` has the case, and it was proved red, then green.
- **Minor, fixed (test).** Empty-query behaviour wasn't pinned. Every active item in name order, as before, is now asserted.
- **Minor, accepted (pre-existing).** A query of `%` or `_` still matches every item through the SKU and barcode `LIKE` arms. Names now match those characters literally. Before this change the name arm matched everything too, so nothing got worse.
- **Nit, accepted.** A query made only of a combining mark matches nothing. That is correct.
- **Nit, accepted.** Every keystroke is still a full scan, as before. Revisit with a folded column only if catalogues pass ~50k items.
