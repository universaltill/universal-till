# 2026-09-09 — Reusable option sets, closing ut-docs#1900

## Context

The card asked for SumUp-style "option sets": a named, reusable, ordered
axis (e.g. "Size: S / M / L") that generates an item's variant range in
one step, kept distinct from checkout-time modifiers. BA verification on
`main` before any code: variants (`item_variants`) and modifiers
(`item_modifier_groups`/`item_modifier_options`) were **already** two
separate, correct mechanisms — the card's stated worry about them being
conflated didn't hold. The real, narrower gap: `item_variants` had no
reusable/named axis concept and no generator; a variant was one free-text
name typed by hand per item.

## Design

- **Migration 017** (`internal/db/migrations/017_option_sets.sql`):
  `option_sets`, `option_set_values` (both shop-wide, independent of any
  item), `item_option_sets` (which sets an item's range is generated
  from, in axis order, capped at 2), and `item_variant_options` — the
  generator's idempotency key. A generated variant is an ordinary
  `item_variants` row; `item_variant_options` is what lets a re-run
  recognise "this combination already exists" without touching or
  duplicating it (the exact re-import-duplication bug class ut-docs#1839
  found in the pilot).
- **`OptionSetRepo`** (`internal/data/option_set_repo.go`), a sibling
  repo to `ModifierRepo` — same "instantiate ad hoc per handler call"
  convention, no `common.Deps` wiring. `GenerateVariants` computes the
  cartesian product across the item's applied sets' values, diffs
  against `combinationKey`s already present (sorted value-ID tuple, so
  it's axis-order-independent), and only inserts what's missing — via
  `CatalogRepo.CreateVariant`, so the inventory-row and stock-untracked
  side effects aren't reimplemented.
- **Auto-SKU fix**: `CatalogRepo.CreateVariant` stored a blank SKU as
  `NULL` instead of generating one, despite the manual add-variant row's
  own "auto if blank" placeholder. Fixed on the shared insert path
  (`generatedVariantSKU()`, retried up to 3x on collision) — covers both
  the manual and the new generator path.
- **UI**: new shop-wide `GET /catalog/option-sets` page (sets/values are
  reusable across items, so they don't belong in the per-item panel);
  an "Apply option set(s) + Generate variants" control added to
  `catalog_variants.html`, purely additive — manual per-variant editing
  is untouched.
- **No ADR** — additive catalog-admin feature following the exact
  structural precedent `ModifierRepo`/#1899 already set.

## Independent review (Opus, isolated worktree, fresh context)

**TDD claims independently re-verified, not taken on trust**: reverted
`CatalogRepo.CreateVariant`'s blank-SKU generation and the
`GenerateVariants` idempotency guard in turn, confirmed each failing test
failed with exactly the claimed symptom, restored, confirmed green again.

**Fixed:**
- **The Items-hub "Option sets" tile was never re-pointed.**
  `internal/pages/items_page.go` still sent it to `/catalog` with a
  subtitle reading "Open an item to edit its variations", and its own
  code comment named this exact card as the reason it wasn't wired up
  yet — #1899 set the precedent of wiring the tile in the same merge
  that ships the destination. Fixed: `Href: "/catalog/option-sets"`,
  subtitle rewritten in all 4 locales, tests updated, screenshots
  regenerated (two 1-byte `sell.png` encoder-noise deltas reverted).
- An orphaned doc comment (`skuAwareError`'s comment had been silently
  captured by the new `optionSetAwareError` inserted above it).
- Added `TestOptionSetRepo_GenerateVariants_DeactivatedGeneratedVariantIsNotResurrected`
  — the "a deactivated generated variant is still present, never
  resurrected as a duplicate" guarantee was documented but untested;
  proved empirically, then folded in as a permanent regression test.

**Accepted as-is:** `GenerateVariants` runs no transaction across the
per-combination inserts, matching this repo's existing best-effort
convention for `CreateItem`/`CreateVariant` (which take `*sql.DB`, not a
`*sql.Tx`, so a transaction would need a signature change beyond this
card's scope).

**Filed as new Backlog cards rather than widening this diff:**
- Deleting/deactivating an option set or a value after variants have
  been generated from it (no delete/deactivate UI ships here; cascade
  semantics need a decision).
- A value rename's effect on already-generated variant names (the name
  is a snapshot at generation time, doesn't follow a rename).
- **The one real latent bug found**: if `CreateVariant` succeeds but the
  following `item_variant_options` insert fails (SQLite `BUSY` is
  realistic on an offline till), the variant persists with no link
  rows — indistinguishable from a hand-added one, so a re-run creates a
  duplicate, defeating the feature's core "always safe to re-run"
  promise. Low-probability; a real fix needs a tx-taking `CreateVariant`.
- Applying a second axis to an item that already generated variants from
  one axis leaves the old single-axis rows stale (undocumented).
- `ErrOptionSetExists` and `ErrOptionSetValueExists` both render the same
  "name already in use" message — wrong wording for a duplicate value.
- The `option-sets` help screenshot shows only the empty state (needs a
  shared seed-data fixture to show real content).

## i18n follow-up (lang-pack-drift)

18 new keys land in `web/locales/{ar,en,fa,tr}.json` this PR. Matching
translations for `ut-plugin-language-{de,es}` are prepared and pushed to
branch `feat/1900-option-sets-keys` on each pack repo, to be opened as
PRs and merged immediately after this PR — the packs' own
`check-key-drift.sh` treats a pack-side key core doesn't have yet as a
hard failure ("orphan"), so they can't land before core without going
red for that reason. This is a separate mechanism from the two repos'
pre-existing, unrelated `categories.*` key drift (from #1898, already on
`main`) found while preparing this follow-up — filed as ut-docs#1925
rather than mixed into this diff.
