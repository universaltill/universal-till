## What shipped

- `internal/enroll/move.go` (new): `Pair` gains a move leg that runs first and
  only when the cloud's `GET /version` says `pair_move: approval-v1`, on a
  main/standalone till holding a live credential. It posts `move:true` with
  the till's current `device_id` and current token as bearer; a 202
  `pending_approval` is held in memory (re-fed by every `/v1/stores/sync`,
  200 and 402 alike); a refusal (`move_*`) leaves the till untouched;
  `move_unavailable`/`device_exists` fall through to today's pairing;
  `move_unauthorized` falls through only when the till has **no** sale or
  close (`HasTradingHistory`; nil hook or DB error count as "has history").
  `DecideMove` signs `{decision, move_id, device_id, source, target, nonce,
  expires_at}` with the till's approval key (UT-1a) and posts it; approve
  adopts the new credential **under the same device id** and resets the
  rollup upload ledger. Three wrong PINs lock + decline the move.
- `internal/pages/move_approval.go` + `web/ui/pages/move_approval.html` +
  `partials/move_approval_notice.html`: nav-level banner (never on the sale
  screen, never a modal), approval page, `POST /api/cloud/move/{id}` behind
  `checkStepUp` (same-origin, manager/admin session, shared PIN lockout) and,
  for approve, the typed target-shop name. Demo mode denies the page and the
  POST; the banner is read-only and allowed.
- `cloudsync.go`: `pending_moves`/`ended_moves` handed to enroll on 200 and
  402. `sales_aggregate_repo.go`: `ResetSalesAggregateUploads`,
  `HasTradingHistory`. Settings → Pair confirm wording switches to the move
  wording when a move would happen; pair refusals translated.
- 48 new `settings.move.*` / `page.title.move_till` keys in en/ar/fa/tr with
  meta; help topic `claim.md` (en/de/ar/fa/tr) gains "Moving this till into
  another shop" and claims the new route.

## Hunt results (the brief's list)

1. **What leaves the till / replay / confused deputy.** The move request goes
   only to the till's own configured endpoint (the same host that already
   receives the token on every sync) over `lantls.NewPeerClient` (pinned
   transport, TLS verified). A QR/code from another shop cannot redirect it:
   the code is posted to *our* cloud, which decides whether that code's owner
   may take the till. The signature binds move id, device id, source store,
   target store, nonce and expiry (`approvalkey.ApprovalMessage`), so a
   captured approval cannot be replayed against another record. Token and
   code never enter logs, errors, URLs or HTML (`TestMoveSecretsNotLogged`;
   `postWithBearer` returns no token in errors). `HX-Redirect` target is a
   UUID validated by `parsePendingMove`. **Fixed (M, below):** the pending
   record was mutable per move id between display and approve.
2. **Authorisation.** Every route refuses a session without the `settings`
   grant server-side (cashier-is-sale-only), re-verified by mutation here.
   `checkStepUp` demands a fresh PIN for approve *and* decline, refuses
   cross-origin before any PIN lookup (so CSRF cannot reach the PIN
   oracle), and shares the device-wide lockout; an empty PIN is a first
   prompt (Err nil) and is **not** counted as wrong. The per-move 3-strike
   count is in memory and per device; a cashier cannot reach it (403 first).
   The sync-delivered move only populates memory; nothing acts on it.
3. **Fail-safe.** Nothing is wiped before the cloud answers; a refused,
   offline, malformed or partial answer returns with the identity intact
   (`TestPairMoveRefusalLeavesTillUntouched`, `TestDecideOfflineSendsNothing…`,
   approve-200-but-unusable keeps the move for a retry). The
   `move_unauthorized` fallback cannot discard sales: any sale/close, or any
   doubt, blocks it. Flag-off path = today's pairing plus one cached
   `GET /version` (5 s timeout, 5 min cache). Replicas never move.
4. **`/version` trust.** A hostile cloud/MITM claiming the capability can
   only make the till do what the cloud can already do with the token it
   already holds; TLS is pinned. A direct 200 on a move (no approval step)
   is adopted — accepted: refusing it would leave the till holding a
   credential the cloud has already re-homed. Note: the cloud on `main`
   always answers 202.
5. **Sync channel.** Same bearer-authenticated `/v1/stores/sync`. Blocks are
   validated field by field (UUID canonical form, nonce/store regexes,
   RFC 3339, lengths); shop names lose control + bidi-override characters and
   are clamped to 80 runes, then wrapped in FSI/PDI and escaped by
   html/template or `html.EscapeString`. **Fixed (M, below):** no size cap on
   what the till keeps.
6. **Offline-first / kiosk.** Banner is `role="status"`, dismissable per
   move/outcome, never over the sell grid, excluded from idle-touch
   (`backgroundPollPaths`, `TestEveryPollerIsClassified` passes). Approval
   page is a full page, no `showModal`; offline → buttons disabled, nothing
   signed or queued, no PIN asked. Checkout is never touched.
7. **i18n/RTL/help.** All 48 keys present and translated in ar/fa/tr (none
   identical to English); meta complete; CSS uses logical properties;
   `inputmode="none"` when the OSK is on; no autofocus. Help prose matches
   behaviour (3 wrong PINs, offline buttons off, refusals, support-key
   wording); `guard-help-*` all pass. German pack draft
   (`scratchpad/s5127/ut1b_de_pack.json`) covers all 48 keys.
8. Dev's open questions (sale-screen chip; re-sent rollups) = #5287, no action.

## Findings

| # | Sev | Finding | Status |
|---|-----|---------|--------|
| 1 | M | `recordPending` replaced a known move id's whole record from a later sync, so the source/target/nonce/expiry *signed* could differ from what the approval page showed (display→approve TOCTOU; needs a hostile or buggy cloud, which already controls the record, so impact is bounded — but the signature's whole point is binding what the manager saw). | **Fixed**: a known id keeps its first-seen record; only `target_name` follows; a mismatching block is ignored and logged. `TestPendingMoveRecordIsImmutablePerID` (fails before, passes after). |
| 2 | M | `pending`/`ended` maps unbounded: a sync answer with thousands of blocks grows till memory until the 24 h prune (binding rule: till caches are budgeted). | **Fixed**: `maxPendingMoves = 8`, `maxEndedMoves = 32`, enforced in `ApplySyncMoves`, `recordPending`, `endMove` (oldest evicted). `TestSyncMovesAreBounded`. |
| 3 | L | `PairWouldMove` performs the `/version` GET synchronously inside the Settings confirm handler: up to 5 s before the dialog renders when the cloud is slow (cached 5 min after). | Accepted for now; the pair itself is online-only. Card if it bites on the Pi. |
| 4 | L | No enforced `frame-ancestors`/`X-Frame-Options` on till pages (CSP is report-only, pre-existing, ut-docs#2913). Clickjacking the approve page would still need the attacker to type the shop name *and* a PIN, so not exploitable here. | Out of scope; already tracked under #2913. |
| 5 | L | The sync response body is read unbounded in `postBody` (`buf.ReadFrom`), pre-existing. Finding 2 bounds what this feature keeps from it. | Out of scope; note for a cloudsync hardening card. |
| 6 | L (UX) | No docs-shots screenshot of the move page (needs a pending move fixture; the id is dynamic) and the reviewer did not re-screenshot — the Tester's driven run is the evidence. Approve is `primary` while the confirm dialog is `Danger`; the red-bordered warning carries the risk, acceptable. | Accept; add a fixture + screenshot when the flag goes on. |

## Verdict

**Safe to merge** (feature is dark: the cloud's `PAIR_MOVE_ENABLED` is off,
so every till keeps today's pairing path plus one cached `/version` read).
