Checked and found sound:

- Double charge / charged-but-unrecorded: one PaymentIntent per idempotency
  key; a collect that completes after a cancel was requested is never
  confirmed; the verdict waits for both the cancel's and the collect's
  completion; a deadline during confirm is `pending`, never `declined`; an
  approval without a PaymentIntent id is rejected by Go as `pending`.
- Unknown → pending: retrieve failure, confirm with no intent, non-succeeded
  confirm, unreadable or unknown-field native reply, context end.
- Credentials: the device Bearer stays in Go; redirects are answered, not
  followed (test fails without `CheckRedirect`, re-verified); no body is
  logged; the connection token and client secret never reach the WebView
  (no `WKScriptMessageHandler`, `TapToPayCloud` is in-process only); Swift
  logs only a PaymentIntent id and a decline code.
- Allow-list: provider and op come from a fixed map, so the URL path cannot
  be steered; refused pairs make no request.
- gomobile: strings only across the boundary; structural assertion in both
  directions; nil un-registers.
- Coordinator: all mutable state is confined to one serial queue; capability
  is read under a lock.
- XcodeGen: the entitlement file is referenced only through the Debug
  config; Release sets it empty; the test target has no host app and no
  package dependency; `Package.resolved` survives `xcodegen generate`.
- No real shop or client name in tests; no secret literals.

## Residual risks

- A cancel can still overtake its collect inside a microsecond window (Go
  cancels between starting the bridge goroutine and Swift queueing the
  attempt). The outcome is `pending`, never a wrong decline, and the native
  attempt still ends at its own deadline.
- If the SDK never completes a collect after a cancel, the coordinator stays
  `busy` until the app restarts. The verdict still returns (`pending`, by the
  bridge's deadline + 5 s backstop).
- The capability is refreshed on connect, setup and foreground only: a
  reader disconnect in between shows as stale "ready" until the next collect
  reconnects.
- StripeTerminal is linked into TestFlight builds with the flag off (binary
  size, two unused usage strings).
- `http://` cloud endpoints (other than loopback) can no longer use the
  payment broker. Intended; an on-prem cloud needs TLS for payments.
- Nothing here has run on a device: Stripe adapter mappings, Apple's sheets,
  backgrounding mid-collect.
