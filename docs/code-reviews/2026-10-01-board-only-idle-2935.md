# Review: idle display boards go board-only (ut-docs#2935)

## What shipped
- `internal/auth`: `Service.ResolveFor(ctx, token, touch, board)`.
  - When a session is idle past `auth.idle_lock_minutes` and the request is a display-board request, the session is **narrowed to board-only** instead of revoked. The flag is in memory, by token hash, and the `idle_lock` audit fires once.
  - A board-only session is served only for board requests and is never touched. Any other request revokes it, including `Resolve`/`ResolveNoTouch` from handlers and `/login`.
  - Board requests are:
    - the board pages and their fragments, plus `/api/orders/stream`;
    - from a board page only (by `Referer`, or `HX-Current-URL`): the order-status and kitchen-resend POSTs, and the shell's own requests (`shellGetPaths`, `shellPostPaths`).
  - Board polls and the stream no longer extend a live session.
- `web/public/app.js`: the client idle timer doesn't fire while a `[data-display-board]` element is on the page. `orders.html` and `kitchen_display.html` carry that marker.
- Help (`users.md`, en/de/tr/fa/ar):
  - The idle-lock step now describes boards that keep running, with everything else going through the PIN pad.
  - It drops the "kiosk counter orders" screen, which no longer exists.
  - The `users` screenshots and the manifest were regenerated (`make docs-shots`). Only the `users` PNGs were committed: the other topics were regenerated byte-noisily in this environment, and nothing about their pages changed.
- e2e: `session-display-board-idle-2935.spec.ts` (auth project). It covers an untouched `/orders` with a 1-minute lock: after 80 s the board is still shown, its poll answers 200, and a full reload keeps it. Then `/settings` goes to the PIN pad, and so does the board afterwards. The spec is added to the fixtures-import guard's exempt list, like the other auth-project specs.
