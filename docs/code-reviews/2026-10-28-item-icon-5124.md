# Review: item icon set on my. shows in the basket line (ut-docs#5124)

## What shipped

Root cause. An icon set on my. arrives as `save_item`'s `icon` and lands in
`items.icon` (migration 066) with no `item_images` thumbnail row (one-picture
rule, `SetItemPicture`). The sell-screen tile, the catalogue list and the
item edit resolve their picture with `ui.ItemThumb` (`iconid.Resolve` over
the thumbnail path plus `items.icon`), so they showed it. The basket line did
not: every `POSRepo` resolver (`resolveItemByID`, `resolveShortcut`,
`resolveSKU`, variant and name tiers, the two scan UNION branches) selected
only the `item_images` thumbnail, `refreshHeldLinePhotos` (held-sale resume)
and `catalog.RefreshBasketPhoto` (live refresh after an edit) likewise, and
`SuggestForBasket` too. A till-set icon is stored as a library tile in the
thumbnail row, which those paths do read, hence "set on the till = shows".
Till to my. was already correct: the snapshot push sends
`iconid.EffectiveIcon(thumb, icon)` (`cloudsync.go`). No ut-cloud or
ut-my-shop change is needed.

Fix. One rule, `iconid.Picture(path, icon)`, now shared by `ui.ItemThumb` and
every basket-line source: all 8 resolver SQL sites also select `i.icon`;
`toShortcutLine`, held-sale resume, `RefreshBasketPhoto` and
`SuggestForBasket` use it. `cloudSaveItem` and the catalogue pull's
photo-replaced hook now refresh the open basket, so a my. icon shows without
a re-ring and never leaves a broken image after its upload is deleted. No
backfill is needed: nothing is stored differently, the column was already in
the till; the basket reads it at ring-up, so existing items show after the
build is installed.
