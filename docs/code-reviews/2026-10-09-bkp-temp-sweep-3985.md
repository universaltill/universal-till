## What shipped

- `internal/stagedupload` gains `BkpDBPattern` (`ut-bkp-*.db`) and
  `BkpDocsPattern` (`ut-bkp-docs-*.zip`), both in `Patterns()`, so the
  existing housekeeping `staged_uploads` sweep (24 h, regular files only,
  never dirs or symlinks) removes the copies a crashed or power-cut .bkp
  import left in the system temp dir. They can be hundreds of MB.
- `internal/catimport/bkp.go` creates both temp files with those constants,
  so the names the sweep matches can't drift
  (`TestPatternsMatchCreateTempNames` iterates `Patterns()`).
- Retention-table policy text now says "upload, import or import preview"
  (startup log/policy map only, not a template).
- Manual: `web/help/*/backups.md` already says "left behind when the till
  stopped in the middle of an upload or import: removed after 24 hours" —
  a .bkp copy is made during an import, so no change.

This supersedes line 44 of `2026-10-09-staged-upload-sweep-3955.md`, which
listed `ut-bkp-*` as deliberately not swept (that review's finding 4, which
deferred it to this card).

Reviewer confirmed, from the code: both temps live strictly inside one
`ParseBkp` call (`defer os.Remove`, `defer docsIndex.close()`; `Result`
carries bytes, never a path; called synchronously from the import handler),
so no live owner can hold one for 24 h. `ut-bkp-*.db` cannot match SQLite
`-journal`/`-wal`/`-shm` sidecars (pinned by tests). A Windows remove
racing a reader fails harmlessly and retries next day. `stagedupload`
imports only the standard library, so `catimport → stagedupload` adds no
cycle. No SQL, no new file writes, no user-facing strings.
