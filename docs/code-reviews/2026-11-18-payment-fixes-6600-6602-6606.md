## 3. universal-till (branch fix/fable-core-pay)

### What shipped
- #6600: `plugins.HandlerExitError` keeps stdout for a non-zero `.authorize` exit (logged through the same redaction). `completeTender` maps `decline_code: outcome_unknown` to `paymentOutcomeUnknownError`: its own toast `pos.toast.payment_outcome_unknown` (200, basket kept), kiosk `selforder.checkout.outcome_unknown` (409). `pos.Service.LockTender` allows only the identical tender (same method and amount per leg, so the same request ids) until it settles. The lock clears on approval, definitive decline, rotate, Reset or Restore.
- #6606: `ref` / `transaction_ref` are redacted by exact name (nested and `recent[]`).
- #6602: captured legs are reversed when a later leg declines and when `pos.CompleteSale` fails (`CompleteSale` returns an error only before commit, verified in `internal/pos/sales.go:1075-1503`). The attempt id is rotated after a reversal. A failed reversal is a Problems warning with method, amount, request id and transaction_ref.
- #6603 (partial): with >1 leg of the method, `original_payments[].refund_amount` is allocated in payment order, capped per leg, and zero legs are dropped.

### Verification
- `go build ./...`, `go vet` (pages, plugins, pos), `go test -count=1 ./internal/plugins ./internal/pos ./internal/pages`: all ok.
- Mutations (all killed): stdout-keep disabled -> `TestHandleEvent_AuthorizeNonZeroExitKeepsStdout` fails; ref redaction disabled -> `TestHandleEvent_PaymentRefsRedactedInRealLog` fails; outcome_unknown branch disabled -> 3 `TestTender_*Unknown*` tests fail; lock check disabled -> `TestTender_OutcomeUnknownLocksTenderUntilSettled` fails; reversal on later decline removed -> `TestTender_LaterLegDeclineReversesCapturedLeg` fails; reversal on CompleteSale failure removed -> both `TestTender_CompleteSaleFailure*` fail; allocation disabled -> `TestTxnRef_SplitCardLegsRefundNamesPerLegAmounts` fails.

### Findings
- **High (must fix before merge): CI i18n-meta guard fails.** `pos.toast.payment_outcome_unknown` and `selforder.checkout.outcome_unknown` have no entry in `web/i18n-meta/en.meta.json` (`scripts/ci/guard-i18n-meta.sh` reports 2 problems). Add `description` + `review: standard`.
- **Medium: any non-definitive error unlocks an outcome_unknown lock** (`internal/pages/pos_api.go`, decline branch after the `HandlerExitError` check). Every other authorize error is treated as a definitive decline: a wasm deadline/timeout, "plugin declares hook but is not loaded", a payment-entries DB error, an `events:receive` denial. All of them run `engine.UnlockTender()` (and, with captured legs, reverse them and rotate the ids). Failure: card leg answers outcome_unknown; cashier taps Pay again; the retry times out or the plugin is mid-reload; the till says "Payment declined, try another method", the lock is gone, and cash is taken while the card charge may stand. That is the exact #6600 double-charge scenario. Fix: only a parsed definitive decline (a `HandlerExitError` with a decline_code other than outcome_unknown, or the plugin's normal decline) may unlock. Keep the lock (and do not reverse or rotate) on transport, timeout or not-loaded errors.
- Medium (card scope, not a code bug): #6602 asks for reversal also when the tender is abandoned (basket cleared, split changed, sale voided). Not built. A basket locked after a later-leg outcome_unknown can still be voided, parked or restored, which clears the lock. The earlier, definitely captured legs are then never reversed, and the only Problems line names the unknown leg, not them. Keep #6602 open, or file a follow-up: on Reset of a basket with captured legs, reverse them or raise a Problems item per captured leg.
- Medium (card scope): #6603 is only half done. Neither plugin reads `refund_amount` yet, so a full refund of a two-card sale is still declined. Allocation is by payment order, so "B returns a 20.00 item" still goes to A's card (the card asks the till to let the cashier pick the leg). Earlier partial refunds are not netted per leg. Keep #6603 open (the PR must say "part of #6603").
- Low: the reversal-failure warning logs the full `transaction_ref` (`reverseCapturedPaymentLegs`). #6602 asks for the reference on the Problems item, but #6606's point is that full refs should not reach the log shipped in diagnostics. Consider masking (tail only, like the plugins' `maskRef`) or putting the full ref only in the Problems item.
- Low (documented): the lock and attempt id live in memory. A restart loses them (#6601 reconcile-on-restart not built).
- Low: no help topic update for the new toast (`web/help/`). The copy is self-explanatory; check whether the POS payments help page lists the toasts.

### Verdict
Changes requested. Fix the en.meta.json entries (CI blocker) and the unlock-on-non-definitive-error path, with a test (locked tender, retry returns a plain transport error, lock still held and a different tender still refused). After that, approve. #6602 and #6603 stay open.
