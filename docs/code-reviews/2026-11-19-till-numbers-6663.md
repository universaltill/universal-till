# Review — till series prefixes, stored sale counters, short order numbers (ut-docs#6663)

Date: 2026-11-19 · Card: universaltill/ut-docs#6663 (with ut-docs#5449 in ut-cloud) · ADR: ADR-0166
"Amendment 2026-11-18" + ADR-0011 item 9 (ut-docs PR #6664, must merge before this PR).

One combined Tester and one combined Reviewer for the batch (till + cloud + ADR). Dev: Sonnet.
Reviewer: Fable (different model), reading the whole diff, not a sample.

## What shipped

- **Stored counters** (`number_series`, migration 108): receipt and invoice numbers come from a stored
  per-series counter written in the sale's own transaction. First use seeds from live + archive rows.
  "Clear transaction history" no longer restarts a series (the table is not in the reset list, not in
  the admin bundle, is in backups).
- **Prefixes**: first main till `1-` (set once at the end of setup, only on a till that has not traded
  and holds no prefix); joined tills `<n>-` from the same never-reused number space as `T<n>-`;
  replacement main till takes the cloud's letter prefix (`A-` .. `ZZZ-`), else `M<8hex>-` as before.
  Existing prefixes (none, `T<n>-`, `M<8hex>-`, `R<4hex>-`) are never renamed.
- **Order number**: digits only, no prefix, the till's own block of 100, goes round inside the block,
  skips numbers still held. Counter orders (`C-`) use the same block rule.
- **Surfaces**: order number large on the thermal receipt, on-screen receipt, kitchen ticket, order
  list / kitchen display, tracking page, self-order confirmation; Journal column + search by either
  number. Help topics `order-status`, `open-orders`, `customer-order-tracking` updated.

## Findings

| # | Severity | Finding | Outcome |
|---|---|---|---|
| F1 | High | Order number stuck on one number. Every completed sale nobody marked "collected" is open by the Order status rule, which is every sale in most shops. After 99 sales the whole block was "held" and the oldest-holder rule (`MIN(created_at)`) returned the same number for every later sale (`1, 1, 1, …`), with a WARN per sale. | Fixed: the newest open holder of a number counts, so a full block reuses the number given out longest ago (round robin); warning once per run. Test `TestNextDisplayNo_NeverCollectedSalesStillGoRound` (failed: `sale 101: "1", want 2`). |
| F2 | High | "Reset after each close" did not reset. Yesterday's uncollected sales held their numbers, so after a close with 60 sales the next order was 61, not 1. | Fixed: with `trading_period_reset` only orders made since the last close hold a number. Test `TestNextDisplayNo_ResetAfterCloseIgnoresLastPeriodsUncollectedSales` (failed: `"61", want 1`). ADR wording proposed on ut-docs PR #6664. |
| F3 | High | Counter orders left their block. `kiosk_counter_orders.display_no` is UNIQUE and held rows live 90 days, so after 99 orders the block never frees and the fallback counted on: `C-100` on till 1, which is till 2's block. Both reach the main till: the ut-docs#2703 collision again. | Fixed: a full block reuses the number of its oldest held row; that row keeps its record under a retired number (`C-12~<rowid>`, the form migration 044 uses). Only a block filled by legacy open/collected rows still counts on. Test `TestCounterOrderDisplayNo_FullBlockStaysInItsOwnBlock` (failed: `"C-100", want C-1`). |
| F4 | High | Restore jump floor ignored the stored counter. `JumpNumbersAfterRestore` took the highest LIVE sale, so on a till that had cleared its history (counter 50001, live 0) the floor was 10000, below the counter, and reserved nothing: numbers the lost till issued after the backup could repeat. | Fixed: the floor starts from the highest of live sales, archived sales, the stored counter and the earlier floor. Test `TestJumpNumbersAfterRestore_FloorIsAboveCounterAndArchive` (failed: `floor 10000, want at least 60001`). |
| F5 | Low | Skip lookup scanned every sale that ever had the number. | Index in migration 108 is now `(display_no, created_at)` and the lookup reads newest first, `LIMIT 1` (108 has not shipped; checksum pin updated). |
| F6 | Low | `TestRender_OrderNoBlockIsDoubleSizeUnderTheHeader` ended on a constant comparison (Tester note). | Replaced by a real check: an over-long value is clipped to `Width/2`. |
| D1 | (Tester) | `.order-no-hero` unreadable in print emulation on dark themes. | Already fixed by Dev; re-run here: `receipt-theme-contrast-4419.spec.ts` 12/12. |
| D2 | (Tester) | `EnrolTill` unreachable. | Already fixed by Dev (`EnrolTillPrefix`); `guard-deadcode-baseline.sh` passes. |

Checked and found correct: uniqueness under concurrency (`_txlock=immediate`, counter bump and INSERT in
one transaction, UNIQUE-conflict retry re-seeds from the full scan and can only move the counter up);
offline (no network in any allocation; `1-` on the local path); upgrade with no counter row (seeds
from live + archive; empty prefix ignores prefixed rows); restore floor applied on every call;
`EnrolTillPrefix` (one transaction, both forms of a number count as used, re-join keeps a valid
prefix, high-water mark); `joinedReceiptPrefix` against an older main till; `SetFirstReceiptPrefix`
guard; cloud prefix accepted only as `^[A-HJ-LNPQSU-Z]{1,3}-$`; restore keeps a letter prefix
(`db` matcher pinned to `data`); legacy numbers are looked up by exact `receipt_no` everywhere (no
code parses a receipt-number shape), so refund, lookup and reprint of `''`/`T<n>-`/`M<hex>-`/`R…`
receipts are unchanged; journal search is a bound parameter with LIKE escaped; no secret, no new
network exposure; no money arithmetic touched.

TDD re-verified by mutation: seeding from `sales` only makes
`TestNextReceiptNo_SeedsFromArchiveWhenNoCounterRow` fail (`000000001`, want `000000006`); restored.

## Deferred (follow-up cards, not blockers)

- A held counter-order row has no link to its held sale, so a paid order keeps "holding" its number
  until the row is pruned or the block goes round. Harmless after F3; a link would free numbers sooner.
- Invoices have no restore floor (receipts and Z reports do); older than this change.
- Settings → "Pair with a shop" and the move flow do not read `receipt_prefix` (ADR section B, known gap).
- The thermal label is the translated "Order %s" with the number removed; correct in the bundled
  locales, a language pack that puts `%s` first would read oddly. Switch to `receipt.order_no_label`
  once Weblate has it.
