# 2026-11-04 — sync sales push halves its batch on HTTP 413 (ut-docs#5428)

**What shipped.** A joined till's sales push (`syncPushSales`) used to send
up to 50 sales in one body and, on any non-200, retry the same body every
tick, so a primary (or reverse proxy) answering `413` stalled the queue
forever. Now:

- `postSalesHalving` (`internal/pages/sync_push_halving.go`) retries the
  leading slice at ceil(n/2) on a 413 (50→25→13→7→4→2→1), in
  `(created_at, id)` order, never reordering or skipping. Only the status
  code is read.
- `sync.push_cursor` moves after each accepted sub-batch, to its last sale
  outside the 5 s settle window, never past a sale without a 200.
- The size that worked is kept in `sync.push_batch_size` and doubles back
  to 50 after a fully accepted tick. One tick makes at most 16 requests, and
  a 413 or the cap never re-kicks the loop early.
- If one sale is still refused at size 1, it holds the queue. Its id goes in
  `sync.push_held_sale`, the replica sync chip goes `warn`, and the keyed
  Problem `sync.push_sale_too_large` names the receipt, logged once. The
  hold clears when the primary accepts that sale. On promote,
  `resolveReplicaSyncProblems` closes the Problem and `ClearReplicaIdentity`
  drops the keys.
- The re-join replay (`rejoin_replay.go`) uses the same helper, with no cap.
  A sale refused alone fails the join and the log line names the receipt.
  The UI shows the existing localised `joinErrUnsentNotSent`, and the data
  is kept.
- Help `multitill.md` (en/de/tr/ar/fa) gained one sentence. The ut-docs
  `architecture/lan-sync.md` and `reference/contracts/pos-lan-sync-journal.md`
  now document the 413 row and per-sub-batch cursor (same cycle, ut-docs
  branch `fix/5428-sync-push-413-docs`).

**Review** (independent subagent, Opus 5.5; Dev was Sonnet):

- **medium: a short accepted tick was stored as a learned limit.**
  **Fixed.** `postSalesHalving` returned the working size clamped to
  `len(batch)`, so with no 413 at all, a normal tick pushing 3 queued sales
  saved `sync.push_batch_size=3`, and a single sale saved 1. In steady state
  (a replica pushes sales as they are rung) the learned size kept collapsing
  to 1–2. A later burst then drained at a few sales per tick instead of 50.
  No data loss, but it is the opposite of the intent. Now the returned size
  is the caller's size unless a 413 shrank it. Regression
  `TestSyncPush413_ShortAcceptedBatchLearnsNothing` fails on the
  pre-review HEAD (`learned size = "3", want unset`) and passes after the
  fix.
- **low (Tester O2): 413 then a non-413 error in one tick skipped storing
  the learned size.** **Fixed.** For example, 413 at 50 then 503 at 25 meant
  the next tick re-sent the refused 50-sale body. `storeSalesPushBatchSize`
  now runs before the error return, with `accepted=false`, so it can only
  shrink. Regression `TestSyncPush413_ThenOtherErrorKeepsLearnedSize` failed
  before the fix (`learned size = "", want 25`) and passes after it.
- **nit (Tester O3 / equivalent mutant M5): the `frozen` flag in
  `onAccepted` was unreachable.** **Removed.** `LocalSalesSince` orders by
  `created_at, id`, and Go compares the same strings in the same order, so
  the settled sales are always a prefix of the batch. A comment now says so.
- **accepted (Tester O1): probing re-sends a refused body every other tick
  when the real limit sits between k and 2k.** This is how additive probing
  works. The refused body is at most about twice the limit, and the same
  tick still halves and sends k sales, so throughput holds. It only matters
  for very large sales. Not worth a separate back-off state.
- Checked, no finding:
  - A sale is never skipped and the cursor never passes an unacked or
    unsettled sale. Each sub-batch's cursor is written only after its 200,
    before the next request.
  - A transport error mid-halving keeps the accepted prefix and the cursor
    stops there.
  - The request cap bounds every path. Halving is at most 7 requests and
    the cap is 16.
  - The push loop is single-goroutine (`runSyncLoop`), so there is no
    concurrent tick.
  - The held key cannot go stale across a re-join: the snapshot restore
    replaces the settings and `ApplyReplicaIdentity` re-seeds the cursor.
  - Repository pattern: no SQL outside `internal/data`.
  - Offline-first: checkout is untouched and the chip is a status dot, not
    a modal.
  - Money untouched.
  - No file writes, so the two recurring bugs (missing `os.MkdirAll`,
    cwd-relative path) do not apply.
