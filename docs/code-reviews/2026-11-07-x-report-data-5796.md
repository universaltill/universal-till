## Behaviour change (flagged)

`CloseShift`'s stored `expected_cash` (and the live expected cash on /shifts) changes for a shift whose `opened_at`
is in the legacy `YYYY-MM-DD HH:MM:SS` format: sales earlier the same UTC day, before the shift opened, no longer
count. A `closed_at` of '' is now read as open. Tester's real-binary run: main stores 1800, this branch 800 on the
same seeded DB. Help note added in `web/help/en/reports.md`.

## Accepted limitation (architect A9)

The X is not read inside one transaction, so a sale committing mid-read can make one X briefly inconsistent; the
next X is correct. The X is never archived.

## Findings

### Medium
**M1 — Voids query now walks every sale of the register instead of only voided rows** (`internal/data/x_report_repo.go:120-126`,
migration 100). Plan with the new index present: `SEARCH s USING INDEX idx_sales_register_completed_dt (register_id=?)`
— the register prefix is used, then every row of that register is read and tested for `status='voided'`.
On main the same predicate planned `idx_sales_status_recorded_dt (status=?)`, i.e. only the (few) voided rows.
On a one-register till with years of sales (Pi, 200k+ rows) every X does an O(all sales) index walk, where the
status index would touch dozens of rows. Not a money bug; a performance regression only on the X (CloseShift does
not run this query). Verified fix (probed, result unchanged 1/700): the documented SQLite planner hint
`AND +s.register_id = ?` in `xVoidsQuery` makes the plan `idx_sales_status_recorded_dt (status=?)`.
Suggest: apply it with a one-line comment, and add a "voids" row to `TestShiftXReport_QueryPlans` asserting
`idx_sales_status_recorded_dt`. Alternative: accept and raise a Backlog card. Either is fine for merge.

### Low
**L1 — `closed_at=''` is "open" to X/`GetShift` but "closed" everywhere else** (`x_report_repo.go:86`;
`CurrentOpenShiftForRegister` :4564 and `LoadShiftForClose` use `closed_at IS NULL`; `ListRecentShifts` :4600
`Open = !closedAt.Valid`). Such a shift can never be closed through CloseShift yet reports as open with an
unbounded window. No code path writes '' (CloseShift stamps RFC3339), only import/restore could. Accept; note for
a later normalisation (`UPDATE shifts SET closed_at=NULL WHERE closed_at=''` migration, or align `ListRecentShifts`).

**L2 — `datetime()` truncates fractional seconds**: a row stamped `…:00.500Z` counts in a shift closed at `…:00Z`
(inclusive bound) and in a next shift opened the same second. Own sales are second-precision RFC3339
(`pos/sales.go:1137`), journaled/imported rows pass through the same `InsertSale`; the second-granularity
double-count at the close/open boundary pre-exists. Informational.

**L3 — Unparsable `completed_at` now excluded instead of text-compared.** Every writer (`InsertSale`, backup import
layouts RFC3339Nano / `YYYY-MM-DD HH:MM:SS` / `…T…`) produces a `datetime()`-parsable value, so no real row is
dropped; the helper comment documents it. Accept.

**L4 — Help wording** (`web/help/en/reports.md:+332`): "whichever way the till recorded the opening time" leaks an
implementation detail into the owner manual; the sentence before already states the rule. Suggest dropping the
clause (would need one more docs-shots hash refresh). Nit.

**L5 — Test nit**: `TestShiftXReport_QueryPlans` checks `"SCAN s "` (trailing space); a bare `SCAN s` line is only
caught indirectly by the index-name check. Harmless as written.

### Checked, no finding
- Index usability: expression spelled identically in query and index (`datetime(s.completed_at)`,
  `datetime(created_at)`); alias-qualified matches. Expression index on `datetime()` has precedent (098/099) and
  the tester's real-binary run applied 100 cleanly.
- Migration on a big table / Pi: `CREATE INDEX` on `sales` inside the migration transaction, same shape and cost as
  099 (which built an index over all sales) — accepted precedent. Append-only, checksum pinned.
- `payments ⋈ payment_methods` inner join: `payments.method_id` has an FK, so no payment row can be dropped from
  Methods; same join as the cash primitive, so Cash and Methods agree.
- Behaviour change is intended and flagged (CloseShift/live expected cash for legacy `opened_at` shifts and for
  `closed_at=''`); the help note ships with it. No en.json keys, no UI surface, no kiosk/modal, no card data.
