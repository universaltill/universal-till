## Decisions

1. **Marks by trigger, unconditional on role and mode.** Every stock write path (sale, receipt,
   count, import, directive, LAN correction) goes through `inventory`, so triggers cannot be
   bypassed; the table is bounded by `inventory`. The role/mode gate is at send time, so a
   replica promoted to main, or a store that becomes cloud-master, uploads what is owed.
2. **Sequence = AUTOINCREMENT of the mark**, not `stock_movements`: movements have no integer
   sequence and are archived and reset. A re-mark replaces the old one under a higher seq.
3. **Stream id for restores.** A DB restored from a backup restarts AUTOINCREMENT below what the
   cloud holds, which would make every upload stale forever. The cloud returns `stored_seq` on a
   stale answer; a stored seq above the row's own makes the till rotate the stream and re-mark
   everything. The request carries `stream_started_at` and the cloud takes a different stream only if it
   started later, so a delayed old-stream request changes nothing (review fix).
4. **Polling loop, not a notification, for the 5 s debounce.** Marks are written by triggers,
   so Go is not told; the loop reads one cheap indexed query every 5 s and coalesces a burst
   into one request. It reads the cached tier, not the socket (works with the socket down).
5. **Rows without a cloud link wait**, they are not sent under the local id. The catalogue
   upload creates the link; the stock upload runs right after it in the same tick.
6. **Poison control.** A location id or a cloud id the cloud would refuse is dropped locally and
   counted by code; quantities are clamped. A batch the cloud refuses with a 400 is bisected to
   the one refused row, dropped only if part of the batch was accepted (otherwise the request
   itself is wrong, the run stops and every mark is kept). The cloud now rejects bad rows per
   row, so the bisect is the defence for older clouds.
7. Per-location rows are uploaded (not summed); the allocation engine sums.

## Known gaps / follow-ups

- Deleted inventory rows and deleted items send nothing; the mirror row stays until the
  catalogue sync tombstones the item (the cloud ignores tombstoned items when reading).
  Owner: allocation engine #4766 must treat a tombstoned item as no stock.
- `0.34.18` in `stockmirror.MinTillVersion` is a guess (latest tag v0.34.17: right only if the next
  release is a patch; `TillVersionOK` passes "dev"/non-semver builds, consistent with the other gates).
- `sales-channel-v1.md` has sections 1-7 only (an earlier draft of this record cited a section 8):
  the payload needs a NEW section in the ut-docs contract. Follow-up for ut-docs, not edited here;
  the exact shape is in ut-cloud `docs/api-reference.md` for now.
- An `unknown_item` row is retried up to 5 times and then dropped; re-marking the item's rows from
  the catalogue pull (an item restored or a variant re-parented) was not built: the pull has no
  simple hook for it, and the row's next stock change re-marks it anyway.
- Rotating the stream after a restore is wired in `app.Run`; the helper is unit-tested and a
  source-level guard pins the call site, but `app.Run` itself is not driven by a test.
- The full Playwright e2e suite is CI-only; not run here.
- Stock-untracked items have no inventory row and so no mirror row (allocation: treat as
  unlimited).
