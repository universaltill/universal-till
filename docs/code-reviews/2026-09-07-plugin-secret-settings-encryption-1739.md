# Code review: plugin secret settings encryption at rest (ADR-0082, ut-docs#1739)

## What shipped

Implements ADR-0082 (Accepted, `ut-docs/adr/0082-plugin-secret-settings-encryption-at-rest.md`) end to end in `universal-till`:

- `plugins.ManifestSetting` gains an optional `type: "secret"` field, validated at manifest parse time (`internal/plugins/manifest.go`).
- New `internal/secrets` package: `Seal`/`Open` (AES-256-GCM, `sealed:v1:`-prefixed base64), and `KeyStore` (file custody modeled on `internal/fiscal/tse_credential_store.go`'s ADR-0053 precedent — 0700 dir, 0600 file, write-tmp-then-rename — generate-on-first-use on a primary/standalone till, lazy one-shot fetch-and-persist on a replica, with a 30s negative-cache/single-flight around the fetch). Package-level `SetDefault`/`Default` singleton, modeled on `internal/httpx`'s `SetDefaultLocale`/`DefaultLocale` (`atomic.Value` — *not* `internal/barcode.Default()`, which has no such singleton).
- `internal/data`'s plugin-settings repo (`plugin_repo.go`) becomes seal/open-aware on every read/write of `plugin_settings.value_json`, gated on the union of a manifest `type: "secret"` declaration or the pre-existing `IsSecretSettingKey` name heuristic (now living in `internal/secrets`, since `internal/plugins` already imports `internal/data` and couldn't be the home without an import cycle; `plugins.IsSecretSettingKey` is a one-line delegate).
- New bearer-authed `GET /api/sync/secrets-key` (mirrors the existing `GET /api/sync/plugins` handler and auth exactly) so a replica till fetches the shop's one AES key from its primary once, lazily.
- `wasm_runtime.go`'s ask/authorize-result log redaction widened to the same field-name list the settings page already masks on, plus a value-shape check that redacts any `sealed:v1:`-prefixed string regardless of field name.

No DB schema change — `plugin_settings.value_json` stays `TEXT`; a sealed value is just a differently-shaped string in the same column, tolerant of legacy plaintext (upgrade-on-next-write).

## Independent review (different model — Opus reviewing Fable's implementation)

Full review ran in an isolated worktree (`isolation: "worktree"`), with real command execution (`go build`, `go vet`, `go test ./...`, `go test -race` on the touched packages, `golangci-lint`, `guard-data-access.sh`) and 5 independently reverted-and-restored mutation checks against the existing test suite, plus its own new adversarial probe. Full findings:

- **Blocker (fixed, this review round):** `secretSettingCheck` (`internal/pages/plugin_settings_page.go`) degraded to the key-name heuristic on ANY manifest-read failure and used that same degraded predicate on the WRITE path — so a manifest-declared secret whose key name the heuristic doesn't catch (e.g. `merchant_code`) was written to `plugin_settings.value_json` in **cleartext with a 200 OK** whenever the plugin's manifest.json couldn't be read (corrupt/unparseable). Reproduced by the reviewer with a temporary probe, then independently reproduced again here with a permanent regression test (`TestPluginSettingsAPI_POST_RefusesWriteWhenManifestUnreadable`) before the fix, confirmed failing, then fixed.
  - **Fix:** `secretSettingCheck` now returns a third value, `resolved`, true only when `plugins.InstalledManifest` returns no error. The GET/display path may still degrade to the heuristic when unresolved (display-only, never an at-rest exposure) — but the POST handler now refuses the ENTIRE save (500, logged) when `resolved` is false, rather than silently downgrading any single key's classification.
  - **Scope note, found while fixing:** the review's own reproduction used a manifest.json that is *absent* as one of its two cases. Making "active version recorded but manifest.json absent" a hard error (my first attempt) turned out to break ~15 pre-existing, unrelated tests across `internal/pages` — that exact DB-row-without-a-file shape is `seedForPages`'s standard, 63-call-site-wide test fixture, not an anomaly specific to this feature. Rather than force a wide, risky rework of that shared fixture (it doesn't run under an isolated `paths.Plugins()` root, so writing real files into it is not obviously safe), the shipped fix narrows the failure condition to what `InstalledManifest` already, correctly treats as an error: the manifest.json file EXISTS but fails to open or parse, or a DB/traversal-guard error occurs. "Active version recorded, manifest.json genuinely absent" stays a tolerated no-op, same as before this card. This is a deliberate, documented scope reduction from the reviewer's literal reproduction, not a silent gap — see `plugins.InstalledManifest`'s doc comment and the Deferred section below.
- **Should-fix (fixed, this review round):** `declaredSecret` was derived by subtraction (`isSecret(key) && !plugins.IsSecretSettingKey(key)`), correct only because `isSecret` happened to be exactly heuristic-or-declared — a derived copy of a rule, and the reviewer flagged it as the structural cause that made the blocker easy to reintroduce. `secretSettingCheck` now returns `declaredSecret` as its own predicate, reading the manifest directly (`manifest.SettingDeclaredSecret(key)`), not inferred.
- **Should-fix (deferred — follow-up cards filed):**
  - A till that joins a shop as a replica keeps whatever local secrets key it already had (if any), rather than adopting the shop's key — a standalone till later enrolled as a replica can end up unable to open the shop's sealed rows, and re-entering the credential there re-seals it under the wrong key and propagates that back to the whole shop. Real, concrete, and worth fixing — but touches `internal/db/replica.go`'s identity-apply path, which is out of this card's already-large scope. Filed as `#1739-followup-replica-key-clear` (see below).
  - `ReconcilePluginSettings` (install-time default-value seeding) bypasses the seal seam entirely — a manifest `default_value` on a secret-typed/credential-named key would land in cleartext at install time. Impact is bounded (defaults shouldn't be live credentials) but the seam's own doc comment claims no caller can bypass it, which this falsifies. Filed as a follow-up.
  - A persist failure after a successful replica key fetch doesn't arm the negative-cache, so a wedged disk can turn every `settings_get` host call into a fresh HTTP request to the primary. Availability, not confidentiality. Filed as a follow-up.
- **Nice-to-have (deferred):** `_key`-suffixed settings aren't name-redacted in `wasm_runtime.go` logging (only the sealed *value* shape is caught, and only for the sealed form, not an opened plaintext a plugin echoes back); no `Cache-Control: no-store` on the secrets-key response; `hostLogWrite` remains entirely unredacted (pre-existing, not introduced by this card); test fixtures use fake `sk_live_*`-shaped strings (obviously fake, no real credential, but a `sk_test_`/`sk_dummy_` prefix would be marginally safer against a scanner); a restore-to-new-hardware operator note for "every secret reads as not configured after a restore" (correct, deliberate behavior per `TestSecretsKeyExcludedFromBackupSnapshot`, just undocumented for the operator).
- **PASS, verified independently, not just re-read:** the AES-256-GCM usage itself (fresh random nonce every call, authenticated decrypt only, no partial/unauthenticated path); the two recurring bug classes this pipeline watches for (`os.MkdirAll` before first write, `paths.Data(...)` not a cwd-relative path) — both clean; fail-closed on write at the repository seam (every writer of `plugin_settings` traced; only the deferred `ReconcilePluginSettings` gap above bypasses it); read-path failure handling (`Open` failure never surfaces ciphertext to a plugin host call or a page response — verified against a real WASM guest, not just the repo function's return value); the new endpoint's auth (same `syncTill` bearer check as every other `/api/sync/*` route, exemption switch entry is an exact string match, not a prefix); the negative-cache/single-flight state machine under `-race`; manifest `type` enum validation (an unknown value is rejected at parse/install time, not silently passed through); the `internal/plugins`/`internal/data` import-cycle claim (verified against the real dependency graph) and that the moved heuristic has no behavioral drift from the original (one-line delegate, not a reimplementation); the log-redaction widening's two claims (the prior list really did miss `api_key`/`auth_value`/etc., and the new sealed-value check really does apply regardless of field name, including inside nested JSON up to the existing depth cap).

## What was verified beyond automated tests

- Five of the implementation's own TDD claims re-verified personally (not just taken on the Dev subagent's word): reverted the relevant guard in the code, re-ran the specific test, confirmed the exact claimed failure message, restored, confirmed green again — for the fail-closed write, corrupt-sealed-value read, secrets-key endpoint auth, exemption-switch coverage, and manifest type-enum validation.
- The blocker's own fix re-verified the same way: wrote `TestPluginSettingsAPI_POST_RefusesWriteWhenManifestUnreadable`, confirmed it fails pre-fix with the exact 200-not-500 symptom, applied the fix, confirmed it passes, then temporarily re-broke the fix (forced `resolved = true`) and confirmed the test catches that too.
- Full gate run clean on the finished tree: `gofmt -l .` empty, `go build ./...` clean, `go vet ./...` clean, `go test ./...` fully green (no `internal/pages` regressions from the manifest-resolution change, 63+ `seedForPages`-based tests unaffected), `golangci-lint run ./...` 0 issues, `bash scripts/ci/guard-data-access.sh` passes (no inline SQL introduced outside `internal/data`/`internal/db`).
- No real client/shop name anywhere in the diff; no secret-shaped literal that isn't an obviously-fake test fixture.

## Safe-to-merge verdict

**Safe to merge.** The blocker the independent review found is fixed and pinned with a regression test; the should-fix that was its structural root cause is also fixed. The three deferred should-fix items are each real but bounded in impact, independently scoped, and tracked as follow-up cards rather than silently dropped — consistent with this pipeline's own "several honestly-scoped commits beat one commit claiming more than it verified" discipline. The nice-to-have items are genuinely optional polish.

## Explicitly deferred (follow-up cards)

- Clear/replace a till's local plugin-settings key file when it applies a replica identity (join), so an already-keyed till adopts the shop's key instead of keeping its own.
- Route `ReconcilePluginSettings`'s default-value seeding through the seal seam.
- Arm the `KeyStore` negative-cache on a persist failure after a successful fetch, not just on fetch failure.
- OS-keystore backing (Linux Secret Service / DPAPI / Android Keystore) — ADR-0082's own explicit, deferred extension point, not attempted here.
- `ut-plugin-payment-stripe`/`ut-plugin-payment-sumup` declaring `type: "secret"` explicitly — ut-docs#1737, blocked on this card, unaffected by anything in this review.
