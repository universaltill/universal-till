# Persistent PSU-underpowered status-bar chip (ut-docs#1232)

**Date:** 2026-09-01
**Card:** universaltill/ut-docs#1232 — "Pi5-1 till runs on an underpowered
PSU (no 5V/5A negotiation) — USB peripheral power restricted; hardware kit
+ install checks must enforce proper supply" (scoped down at grooming to
its product + hardware-track pieces only — see "Out of scope" below)
**Complexity:** medium (Dev: Sonnet inline; Review: Opus subagent, per
model-routing rules)

## What shipped

A Raspberry Pi whose power supply can't negotiate a full 5V/5A over USB-C
PD restricts USB peripheral current — the till's own touchscreen is USB —
with only a boot-time/desktop-level warning nobody watching a kiosk (no
desktop chrome) would ever see. This adds a local, offline, best-effort
check and a persistent status-bar chip surfacing it.

- **New package `internal/pihealth`**, mirroring `internal/updates`'
  existing shape exactly (package-level `atomic.Value` `Status`,
  `Current()`/`CheckNow()`/`Start(ctx, wg)`, every failure silent, a
  complete no-op on any non-Raspberry-Pi platform). Two local signals,
  either sufficient on its own:
  - `vcgencmd get_throttled` bit parsing — bit 0 (under-voltage now) or
    bit 16 (under-voltage since boot, sticky). Needs the rail to have
    actually sagged under load.
  - The negotiated PSU max-current, read directly from the device tree
    (`/proc/device-tree/chosen/power/max_current`, a big-endian `uint32`
    in mA) — below 5000 mA means the firmware already decided the
    attached PSU can't do 5A and capped USB peripheral current
    accordingly, catching the problem immediately at boot before any load
    trips the vcgencmd bits. Missing node (Pi 4 and earlier, no USB-PD
    negotiation) reads as "no signal," not a false problem.
  - Raspberry Pi detection via `/proc/device-tree/model` (the standard
    Raspberry Pi OS/Debian file) — absent everywhere else, including a
    container without the host device tree bind-mounted.
  - Once latched true, status stays true for the process's life (a
    reboot on a proper supply starts a fresh process with a clean
    `Status{}`) — a transient read failure or the rail recovering under
    lighter load must not make an already-shown warning silently vanish.
- Wired into `internal/httpx/httpx.go`'s `baseFuncs` (`psuunderpowered`
  template func, same pattern as `updateavailable`) and
  `internal/app/app.go`'s startup (`pihealth.Start(bgCtx, &wg)`, right
  next to `updates.Start`).
- New persistent chip in `web/ui/layouts/base.html`'s status bar — a real
  `<a href="/help/power-supply">`, not an inert span, so the remediation
  text is reachable on a touchscreen with no hover; reuses `.sb-item` and
  the existing `--warning` CSS token.
- New i18n keys `status.psu_underpowered` / `status.psu_underpowered_hint`
  in all four locales (en/fa/tr/ar) — fa/tr/ar translated directly by this
  pipeline (the self-hosted Ollama NAS is unreachable from this cloud
  session, same disclosed limitation as PR universal-till#710).
- New help-manual topic `web/help/{en,fa,tr,ar}/power-supply.md`, no
  `routes:` claim (mirrors `updates.md`'s own shape — a status-bar chip
  explained as its own topic, not tied to one page's route).
- `make docs-shots` re-run (render-jitter only, no new UI screens).

## Independent review

An Opus subagent reviewed the diff independently, in an isolated worktree
branched from a WIP commit, with no visibility into the Sonnet
implementation reasoning.

**Verdict: not safe to merge as submitted — one blocker, three should-fix,
three nitpicks. All addressed before this commit.**

- **Blocker (fixed):** the original second signal shelled out to `dmesg`
  and grepped for `"not capable of supplying 5v at 5a"` — both the wording
  and the source were wrong. The real Raspberry Pi source string omits
  "at 5A" entirely, varies across tools/locales, and — more fundamentally —
  is generated by **userspace** tooling (`pplug-power`, `pemmican`) reading
  the device tree, never logged to the kernel ring buffer at all
  (`repo:raspberrypi/linux "supplying 5A"` → 0 hits). On the exact device
  in ut-docs#1232 (boot warning fired, vcgencmd bits still clear), this
  signal would never have fired — silently defeating the entire reason the
  card was scoped this way. The reviewer traced this to source
  (`raspberrypi-ui/pplug-power`'s `po/en_GB.po`, `waveform80/pemmican`'s
  `power.py`) and identified the real, structured signal: the device tree
  node those tools themselves read. Replaced the whole `dmesg` signal with
  a direct read of that node (`negotiatedCurrentBelowThreshold`,
  documented above) — the same local, offline, no-root-needed shape, and
  actually the "PSU max-current sysfs" the original card asked for.
  The reviewer also flagged that the removed `dmesg`-based tests were
  tautological (asserting against the same invented string the
  implementation searched for) — replaced with tests against real
  negotiated-current values (3000/5000/5001/0 mA, node absent).
- **Should-fix (fixed):** status wasn't latched — recomputed from scratch
  every 5 minutes, so a transient read failure or the rail recovering
  under lighter load could flip an already-shown chip back off while the
  PSU was still wrong, contradicting the chip's own copy and the help
  topic's "stays until reboot on a proper supply" claim. Fixed:
  `checkOnce` now short-circuits once `Current().Underpowered` is true and
  never re-derives it false. New regression test
  `TestCheckOnceLatchesOnceTrue`.
- **Should-fix (fixed):** the chip's amber fill used light ink
  (`#fff7ed` on `#d97706`, ~3:1) — fails WCAG AA for the status bar's
  ~12.5px bold text (needs 4.5:1; not "large text"). Changed to dark ink
  (`#451a03`, ~4.7:1).
- **Should-fix (fixed):** a broken sentence in `web/help/en/power-supply.md`
  ("The built-in checks the device itself already reports...") — missing
  subject/verb; the fa/tr/ar translations had already rendered the
  intended meaning correctly, so only the English regressed. Rewritten.
- **Nitpick (fixed):** the remediation text lived only in `title=""`,
  unreachable on a touchscreen with no hover. Made the chip a real link to
  its help topic (`/help/power-supply`, via the manual's existing generic
  `GET /help/{topic}` route — no new `routes:` claim needed) instead of a
  plain span; added a matching hover treatment.
- **Nitpick (fixed):** one test case name claimed `0x50000` meant
  "under-voltage now and since boot," but bit 0 (now) is clear in that
  value — it's bits 16+18 (since-boot + throttling-occurred). Renamed, and
  added the actually-missing "bits 0+16 together" and "bit 2 (currently
  throttled) must be ignored" cases.
- **Nitpick (moot after the blocker fix):** the removed `dmesg` signal
  re-buffered up to ~1MB of kernel ring buffer every 5 minutes for an
  answer that couldn't change after boot — gone along with the signal
  itself.
- Confirmed genuinely clean, no changes needed: bit-masking (`0x1|0x10000`,
  correctly excluding the frequency-cap/thermal bits), `isPi()`'s
  three-way correctness (ENOENT, non-Pi model, real Pi model),
  `atomic.Value` type-consistency across every store site (no
  `nil`/pointer/mixed-type panic risk), goroutine/`wg` lifecycle (`Add`
  before spawn, both `select`s honor `ctx.Done()`, `exec.CommandContext`
  killed on cancel, no wedge against `drainBackgroundServices`), both
  recurring bug classes (no file writes at all, so no missing-`MkdirAll`
  class; the one path used is an absolute kernel pseudo-file correctly
  *not* routed through `paths.Data(...)`), RTL/i18n (all four locale keys
  present, `.sb-power` correctly added to the 480px ellipsis breakpoint,
  no new hardcoded color besides the reused `--warning` token), the help
  topic's structural mirroring of `updates.md`, and no secret-shaped
  literals or real client/shop names anywhere in the diff.
