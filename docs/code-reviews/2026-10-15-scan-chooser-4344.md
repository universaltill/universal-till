# Scan chooser: a code that is two things asks (ut-docs#4344)

**Status: WORK IN PROGRESS. NOT YET REVIEWED.** This branch was pushed so the work survives a shutdown. Do not merge until the independent review below is done and recorded.

## Built so far
- `/api/pos/scan` looks a code up as every kind: item (exact), voucher, customer (only `CUST*`/`LOY*` codes), promo and receipt (`internal/pages/scan_resolve.go`).
  - One answer acts exactly as before.
  - Two or more render `Basket.ScanChoices`, a chooser at the top of `#basket`. Nothing is added until the cashier picks a row, which re-posts with `kind=`.
  - Tiles, suggestion chips, the identify pick and `gv=1` always mean the item.
- `POSRepo.ScanCodeKinds`: one query for the voucher, promo and receipt checks. The promo predicate is shared with `FindActivePromo`.
- Keys `pos.scan_choice.*` in en/tr/fa/ar. Help in `sell.md` for en/de/tr/fa/ar. CSS adds `.scan-choices` to the phone collapsed-basket whitelist.

## Verified so far
- Handler tests: 8 cases (item×voucher/promo/receipt/customer, `kind=` each way, tile, repeat scan). All failed first, now pass. `go test ./...` and `go vet` clean. i18n, data-access and help-topics guards pass.
- Playwright `scan-chooser-4344.spec.ts`: 6 pass.
  - Mutation: dropping the phone whitelist fails both phone cases.
  - Screenshots read at 1024×600 (en), 360 px (en) and 360 px (fa, RTL). Amounts use the shop's currency and the locale's digits.
- `BenchmarkScanItemOnly` against the pre-change base:

  | case | before | after | change |
  |---|---|---|---|
  | scanner first | ~720 µs | ~680 µs | faster: the item is resolved once, not twice |
  | scanner repeat | ~590 µs | ~530 µs | faster |
  | typed first | ~597 µs | ~640 µs | +40 µs (+7%) |

  The typed-entry cost is the one combined existence query, the irreducible price of checking the other kinds.
