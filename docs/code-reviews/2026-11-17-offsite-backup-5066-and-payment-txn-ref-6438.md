Independent combined review (did not write the code). Inputs: the 8 worktrees' uncommitted diffs, /tmp/tabletfix/tester-batch.md. No source edited. Re-ran nothing the tester already mutation-proved (6438 host+plugin P1/P2 mutations accepted from the tester report).

Verdict: 6438 = APPROVE with 3 small fixes (all Low/Medium). 5066 = DO NOT MERGE until H1, H2, M1 and the tester's 4 FAILs are fixed (H1/H2 are silent, unrecoverable key loss).

## HIGH
H1. universal-till/internal/offsitebackup/keystore.go:94 (loadFile) — a READ (Load/Older/HasKey) deletes the shop key file when storeID=="" or differs. Callers pass uploader/restorer `liveStore()` (service.go:55), which returns "" on any transient `settings.Get` error (SQLite busy under sales) when cfg.Marketplace.StoreID is empty. Reachable from GET /backups/cloud-key and the card render (`HasKey`, service.go:87), ApplyKeyChoice, Restorer.run (restore.go:~410, `sid` unchecked), keyStep. Scenario: shop with "no cloud copy" (E1 default-off path), busy DB at the moment the Settings card renders -> key file removed -> every backup in the cloud is permanently unreadable (cloud holds fingerprint only); the saved UTK1 string is the only way out and the owner may never have exported it. Fix: Load must never delete; return ErrNoKey on mismatch/"" and delete only in the explicit leave-shop hook; guard all callers against sid=="" (ensureKey does, the others do not).
H2. universal-till/internal/enroll/pair.go:213 + offsitebackup/service.go OnStoreLeft hook — `resetIdentityForPair(!replica)` deletes the key file BEFORE the new pairing has succeeded and without checking whether the till is re-pairing to the SAME shop (re-enrol after token loss/"replaced" flow). Scenario: owner re-pairs the main till to the same store, pairing fails or succeeds, key gone, escrow off -> old backups unreadable. Also uploader.go:365/431 `u.Keys.Delete()` wipes the whole file incl. `Older` generations on a 409. Fix: delete only after the new store id is committed and differs from the key's StoreID; on 409 delete only the generation just created.

## MEDIUM
M1. ut-cloud/internal/api/app_endpoints_backups.go:67 (DELETE .../backups/key, no step-up) + tillbackup/keys.go:252/270 — one owner session call (or a compromised main-till token via DELETE .../key/escrow, no owner involvement) irreversibly drops every wrapped key copy and blocks a new one. With the till lost/wiped, backups become unreadable. A hijacked owner cookie/CSRF-less XHR is enough; "reduces exposure" ignores the data-loss side. Fix: require requireStepUp (as for allow) or a 24 h delay/undo + mail; make till-side DeleteEscrow refuse unless the till proves it holds the key (fingerprint check) and mail the owner.
M2. ut-cloud/internal/tillbackup/upload.go:57-110, retention.go:28 — `taken_at` is till-supplied and unbounded (no <= now+skew, no >= now-31d). A future date is "always newest" (never pruned); a same-day garbage upload (content never verified, cloud only counts parts) replaces the good backup of that day under "newest per day" and Prune deletes the good one's blobs at once (Azure soft-delete 14 d is the only net). Compromised till token = ransom/overwrite of 30 days of history (bounded by BeginsPerDay=4). Fix: validate taken_at window; never prune on a backup that was not yet restore-verified, or keep the previous complete same-day backup until the next day.
M3. universal-till/internal/offsitebackup/restore.go:445-457 — the till uses the cloud's `poll.BackupID` and `poll.Parts` and never checks `poll.BackupID == backupID` that the manager chose/owner approved. A compromised or buggy cloud can substitute another (older, rollback) backup of the same shop; the owner approved a specific `taken_at`. Fix: compare, fail ErrCodeCorrupt on mismatch; also cap `len(Parts)` and the sum of `Bytes` (<= MaxBytes+8 MiB) and check free disk before download (no AC1.5 equivalent on the restore path; disk fill from a hostile answer, cap is only 1 MiB of JSON = ~10k parts x 8 MiB).
M4. 5066 ADR number collision: origin/main already has adr/0195-records-cleanup-adr-stubs-and-review-digests.md (#6469, 5656d5a7). The worktree adds a second adr/0195-off-site-... and every comment/doc/code string cites "ADR-0195". Binding-ADR index (guard-adr-index) will fail or silently shadow. Fix: renumber to the next free number (0196 is taken by 6438, 0197 reserved IAP per memory: use 0198 or next free after a fetch) in ADR file, README row, design note and all repos' comments/help.
M5. Tester FAILs (confirmed as blockers, CI red): (1) internal/auth TestEveryPollerIsClassified — wait: middleware.go now lists /ui/backup-cloud-restore/status in backgroundPollPaths (diff line 410) so re-run, may already be fixed after the tester ran; (2) TestNoUnrecoveredGoroutines: bare `go` at offsitebackup/restore.go:217 (flagged despite RecoverAndLog; add `// goroutine-recover:allow` or restructure), restore.go:643, uploader.go:559 (sealFile gzip goroutine HAS RecoverAndLog at 560 but guard wants it on the go line); (3) plugins TestReservedPageRoutesCoverLiteralChildNamespaces: /backups missing from reservedPageRoutePrefixes (plugins/manifest.go:819) so a plugin page could shadow /backups/cloud-key and /backups/cloud-restore, security relevant; (4) e2e restore-cloud-cashier-5066.spec.ts not in AUTH_ONLY_SPECS and sorts before login.spec.ts. Cashier-denial itself (server-side `deny` -> data_management) was verified by the tester when run in the auth project; code review agrees (every mutating route calls deny/checkStepUp; only /api/offsite/now uses checkOrElevate, same as "Back up now").

## LOW
L1. offsitebackup/restore.go:230 / pages/offsite_backup_api.go:487 — POST /api/offsite/recover/cancel calls `Restorer.Wait()` with no timeout; a restore stuck in importAndStage/BeforeStage (large DB, 4 GiB) blocks the HTTP handler for minutes; also the wait() loop (restore.go:~262) retries forever on network errors until the cloud request expires (cloud answers `expired`, ok) but with no overall cap if the cloud is unreachable (goroutine lives until Cancel). Add a deadline.
L2. restore.go keepReleasedKey/runLink — a key released by the cloud is saved without checking `Fingerprint(dek) == poll.DEKFingerprint`; a corrupted/forged release plants a wrong key and the till then uploads backups under it (cloud's begin check uses the registered fingerprint so begin would 409, but `runLink` saves before any check). Verify fingerprint before Save.
L3. ut-cloud restore code: 8 chars Crockford (40 bit), unsalted SHA-256, in the URL query of both the QR deep link (`approve_url`) and GET .../restore-requests?code= (query strings reach reverse-proxy/access logs). Mitigated by owner-only, 5 attempts, 15 min TTL, single use. A GET with a side effect (wrong code increments attempts on EVERY pending request of the store, app_endpoints_backups.go:111 -> owner.go:154/188) lets one typo burn all waiting requests; use POST. Pass the code in the fragment or a POST body.
L4. ut-cloud keys.go:229/EscrowKey — DEK arrives at the cloud in the clear in the request body (TLS only) and is held in process memory; zeroed after wrap (ok). Documented trade of §15; ensure the privacy text on my. and till says "we can decrypt" when on (ADR text does). No log/DB/blob leak found; tester's bridge scan agrees. PollRestore: if the answer carrying the DEK is lost (network), the approval is burned (consumed, key released=true) and the owner must re-approve; acceptable, but worth a help line.
L5. universal-till/internal/pages/offsite_backup_api.go:~215 keyStep — key string rendered into HTML and a `data:` URL; no-store set, PIN step-up and cashier denial present. Fine. `GET /ui/backup-cloud-restore/status` shows the approval code to any manager (intended).
L6. 5066 uploader.go:207 — a plaintext stripped DB copy `offsite-*.part` (mode 0600, removed by defer/sweepTemp) sits in the backups dir during sealing; fine, but it is in the dir the "copy a backup off this till" feature lists/serves? Verify `db.ListBackups` / download handler skips `offsite-*` (IsUploadedBackupName covers only uploaded names).
L7. 5066 no `taken_at`/size sanity on Complete (`PlaintextBytes` till-claimed); metadata only.

## 5066 verified-good
AEAD: per-backup key = HKDF(DEK, salt=cloud backup_id, info=store id); random 7-byte nonce prefix + u32 counter + last flag, whole 32-byte header as AAD, truncation/reorder/extension/trailing bytes all ErrCorrupt (format.go:105-226); no nonce reuse (fresh key per backup + random prefix). Cloud never decrypts; begin returns no key; fingerprint is HKDF-free SHA-256 of a 256-bit random key (no brute-force oracle). DEK file 0600/dir 0700 atomic write, outside SQLite, not in snapshots/restore (RestoreDropKeys covers settings). Release: owner-only route (appStoreAccessTable Owner), fresh step-up before approval, code hash compared constant-time, request bound to store+device (`ownRequest`), consume is a conditional UPDATE (single release, concurrent polls lose), unwrap before consume, key released only when till lacks generation and a copy exists, parts only served to the consuming device inside the 2 h window, audit + owner mail every time. All queries filter StoreExternalID from the authorized token (no IDOR found); blob keys are `backups/<store>/<backup>/part-N` inside the tenant bucket; PutPart bounds: 411 without Content-Length, MaxBytesReader, hash-before-commit. Restore path: file name from validated UUID only (parseUUID rejects '/' and '.'), import reuses db.ImportBackupFile (other-shop, newer schema, 4 GiB cap, identity stripped) and StageRestore; no zip involved. Goroutines: single-flight uploader, one restorer, bounded state (in-memory RestoreState only), 1 MiB JSON caps, 4 KiB error caps.

## Resolved (dev fix pass, 2026-11-17, uncommitted)

- **H1** `offsitebackup/keystore.go`: `Load`/`Older`/`HasKey` never delete the key file; a mismatching or empty store id (a transient `liveStore()` "") is just `ErrNoKey`. Only `DeleteForStore(oldStore)` removes a file, and only the one for the shop left. Tests: `TestKeyStoreSaveLoadModesAndStoreBinding` (reads with "st_2" and "" leave the file and key bytes intact), `TestDeleteForStoreOnlyRemovesThatShopsKey`.
- **H2** `enroll/pair.go`, `move.go`: `resetIdentityForPair` no longer runs the hook; it returns the left store id, and `storeLeft(old, new)` fires `OnStoreLeft(old)` only after `adoptPaired` committed and only if the shop differs (same-shop re-pair, failed pairing, replica: no call). `uploader.go` 409 `key_exists` (register, StartNewKey) keeps every generation. Tests: `TestStoreLeftHookRunsOnlyAfterPairingToADifferentShop`, `TestKeyExists409KeepsEveryKeyGeneration`, `TestLeavingTheShopDeletesTheKeyFile`.
- **M3** (least privilege): the till no longer calls any delete of the cloud copy (`DeleteKeyEscrow` removed from the client; choice "off" only stops sending); ut-cloud removed `DELETE /api/v1/stores/backups/key/escrow` and `Service.DeleteEscrow`; the owner route `DELETE /ui/app/stores/{id}/backups/key` now needs `requireStepUp` (my. panel prompts the sign-in). Tests: `TestAppBackupKeyCopyDeleteAndAllow` (stale session = 401 step_up_required, nothing written), `TestTillBackupKey_*` (device DELETE does not drop the copy), `TestKeyChoiceOnThenOffNeverDeletesTheCloudCopy`, my-shop `a delete on a stale sign-in shows the sign-in prompt`. Docs: ADR, design note, operations.md, api-reference.md, both help topics.
- **M4** ADR renumbered 0195 -> **0199** (origin/main has 0195 records-cleanup; 0196 is 6438 and free on main; 0197 IAP and 0198 Tap to Pay are open PRs). All citations in the four worktrees and `adr/README.md` updated.
- **M6** ut-cloud `tillbackup/upload.go`: `taken_at` must be within now+10 min and now-31 d, else 400 `invalid_request`. Test: `TestTillBackup_BeginBoundsTakenAt`.
- **M7** `restore.go`: the cloud answer's `BackupID` must equal the approved one (else corrupt); part list capped (count, 1 byte..8 MiB each, total <= MaxBytes+8 MiB, else too_large/corrupt); free disk >= 2x the download checked before any part is fetched. Tests: `TestRestoreRefusesAnotherBackupThanTheApprovedOne`, `TestRestoreCapsPartCountAndTotalBytesBeforeDownloading`, `TestRestoreChecksFreeDiskBeforeDownloading`.
- **L1** `Restorer.WaitTimeout` (cancel handler waits at most 5 s); polls stop after 10 min of continuous failure (`GiveUpAfter`). Tests: `TestWaitTimeoutReturnsFalseWhileTheRestoreRuns`, `TestRestoreStopsWhenTheCloudStaysUnreachable`.

- **L6** verified: `ListBackups`/`ValidBackupName` only know `unitill-pos-*.db`, so `offsite-*.part`, `offsite-*.utbk`, `restore-*.part` are never listed or served; pinned by `db.TestOffsiteWorkingFilesAreNeverListedOrServedAsBackups`.
