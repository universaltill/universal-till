# Review — main till serves TLS on its LAN port (ut-docs#2736, slice A)

- **Date:** 2026-10-10
- **Card:** ut-docs#2736 (ADR-0114 §7), slice A: the main-till side. The
  pin at pairing and the pinned `https`/`wss` peers are separate cards.
- **Author:** Opus 5.5 (cloud session). **Reviewer:** Fable, independent,
  in a detached worktree.

## What shipped

- `internal/lantls` creates the till's LAN TLS identity.
  - One self-signed ECDSA P-256 key under `paths.Data("tls")`: directory
    0700, `key.pem` and `cert.pem` 0600, written atomically (temp file,
    fsync, rename, fsync of the directory).
  - The cert is valid for 5 years and carries no hostnames.
  - It is re-issued on the **same key** (so the same pin) when it is
    missing, belongs to another key, or is within 30 days of `notAfter`.
  - An unreadable, non-PEM or non-P-256 key is never overwritten,
    because a new key would silently change the pin. The till then
    serves plain HTTP only.
  - `Pin()` is the hex SHA-256 of the SPKI.
- `lantls.Listen` sniffs the first byte of each connection off the accept
  path, one goroutine per connection.
  - `0x16` → `*tls.Conn` (TLS 1.3 only, ALPN `http/1.1`), so net/http does
    the handshake and sets `Request.TLS`.
  - Anything else, or 10 s of silence → plain HTTP, as before.
- `server.Start` wraps the bound listener (`withLANTLS`). Demo tills
  (ADR-0113) stay plain. Any key failure logs
  `[LAN TLS] serving plain HTTP only: …` and serves plain HTTP: TLS never
  fails a request.
- `internal/server` `TestMain` points `paths` at a temp dir, so `Start`
  in tests no longer writes a private key into the source tree. That
  happened on the first run and was caught there. `.gitignore` also
  ignores `**/data/tls/`.

## Findings (Fable)

| # | Severity | Finding | Outcome |
|---|---|---|---|
| 1 | should-fix (borderline blocker) | `peekedConn` embedded the `net.Conn` interface, hiding `*net.TCPConn.CloseWrite`. net/http's lingering close was skipped, so an early 401/413 to an unread POST body could reach the client as a reset. | **Fixed.** `CloseWrite` is forwarded. `TestSniff_PlainConnKeepsTCPInterfaces` fails without it. |
| 2 | should-fix (perf) | Same cause: `io.ReaderFrom` (sendfile) was lost for plain `ServeFile`/backup downloads. | **Fixed.** Covered by the same test. |
| 3 | nit | `Accept` could hand Serve a new conn after Close began (random `select`). Conns still being sniffed stayed open up to 10 s after Close. | **Fixed.** `Accept` checks `done` first, and a watcher interrupts the `Peek` on Close. `TestSniff_CloseClosesConnsStillBeingSniffed` fails without it. |
| 4 | nit | No directory fsync after rename: a power cut right after first boot could lose the new key, so the next boot gets a new pin. | **Fixed** (non-Windows). |
| 5 | nit | A `chmod 0700` failure (vfat/exFAT data dir) would turn TLS off for good. | **Fixed.** It is logged, not fatal. The key file is still created 0600. |
| 6 | nit | Coverage gaps: wrong-type key, Close mid-sniff, hijack/LocalAddr. | Added a wrong-type-key test and the Close test. Hijack and `LocalAddr` forwarding were checked by reading the code (the reviewer did the same): `hostIsThisTill` uses `LocalAddr`, which both wrappers forward. No new test for those. |

Also tried and dropped: a behavioural "early 413 survives" test. It passed
even with `CloseWrite` removed, so it could not prove the fix. The
deterministic interface assertion replaces it.

## Verified beyond unit tests (driven run)

A real `go build` binary was run on `127.0.0.1:18765` with a fresh
`UT_DATA_DIR`:

- `curl http://…/healthz` → 200, and `curl -k https://…/healthz` → 200
  over HTTP/1.1, on the same port.
- `openssl s_client -tls1_2` → alert 70 (protocol version), so TLS 1.2 is
  refused.
- `data/tls` is 0700 and both files are 0600. The cert has
  `CN = Universal Till LAN` and runs from now−1h to +5 years.
- The SPKI SHA-256 of the served cert (openssl) was identical across three
  boots, so the pin is stable.
- The first draft logged the pin at startup, but the log redactor masks
  long hex. The line now just says TLS is being served.

Gate:
- `gofmt` clean, `go vet ./...` clean, `golangci-lint` 0 issues.
- `go test -race ./internal/lantls ./internal/server` passes; the full
  `go test ./...` result is in the PR.
- No UI, locale keys, SQL or migrations are touched, so the user manual is
  unaffected: nothing a shop owner sees changes.

## Exposes

A TLS endpoint on the port the till already serves, and one private key
under the data dir (0600). Nothing new leaves the LAN, and plain HTTP
behaves as before.
