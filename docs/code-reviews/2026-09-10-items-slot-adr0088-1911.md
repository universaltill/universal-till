# Code review: ut-docs#1911 — /items section list as an ADR-0088 UI slot

**Author:** Pouria Teimouri (`lane:cloud-41`), implemented inline (Sonnet, `complexity:medium`)
**Reviewer:** independent Opus subagent, isolated worktree (`complexity:medium` → Opus per model-routing)

## What shipped

`internal/pages/itemsnav`'s hardcoded `Sections` slice (the `/items`
left-rail section list) is now resolved through `internal/uislot`'s
ADR-0088 declarative UI-slot registry — the same mechanism the Menu
launcher already used — so a `layout` plugin can relabel and reorder it,
not just the Menu tile.

- `internal/uislot`: added `ItemsSlot`, `CoreItems`, `ProtectedItemsKeys`,
  generalized `ParseMenuAmendments`'s body into a shared
  `parseSlotAmendments(pluginID, spec slotSpec, config)`, added
  `ParseItemsAmendments` and a slot-dispatching `ParseAmendmentsJSON`, and
  made `FindConflict` slot-scoped (`Amendment.Slot`).
- `internal/pages/itemsnav`: `Sections` → `Resolve(locale, amendments)`.
- `internal/pages/common`: `Deps.ItemsAmendments`/`ItemsAmendmentsSnapshot`
  (mirrors `MenuAmendments`), `BuildItemsAmendments`, and a slot filter
  added to the existing `BuildMenuAmendments` (the amendment pool is now
  flat across both slots).
- 5 call sites (`items_page`, `categories_page`, `inventory_page`,
  `catalog/handlers` ×3) updated to resolve and pass the Items rail.
- `internal/plugins`: `loadLayoutEntries`/`validateLayoutEntries` route
  through the new dispatcher; the within-manifest duplicate-key check is
  now slot-scoped.
- `plugins/layout-salon`: a second `layout` entry demonstrates the Items
  slot (relabels `/catalog` to "Services", reusing the existing
  `layout.salon.services` key — no new translations). Version 0.1.0 →
  0.2.0.
- Tests: new/extended coverage in `internal/uislot`, `internal/pages/itemsnav`
  (new file), `internal/pages/items_page_test.go` (an end-to-end test
  installing the real `plugins/layout-salon/plugin.json`), and
  `internal/plugins/layout_validation_test.go`.
- `web/help/{en,de,fa,ar,tr}/menu.md`: corrected — the layout-plugin
  section no longer claims a `layout` plugin "only changes what the Menu
  shows."
- `reference/plugin-manifest.md` (ut-docs repo): documented the `items`
  slot's schema, key set, and its narrower capability set.
- `web/help/img/manifest.json` + regenerated screenshots (`make docs-shots`
  — required by `guard-docs-shots.sh` whenever `internal/pages/**.go`
  changes; the zero-plugin render is pixel-identical everywhere except a
  handful of antialiasing-noise pixels the independent review measured and
  attributed to Chromium version drift, not a real UI change).

## Independent review — findings and disposition

Reviewed by a fresh-context Opus subagent in an isolated worktree, with
its own build/vet/lint/full-test-suite run (not trusted on my word). It
found two real blockers and several real medium findings; nothing was
dismissed as wrong.

| # | Severity | Finding | Fix |
|---|---|---|---|
| 1 | **Blocker** | `/items` panics (`sections[0]`, index out of range) if a `layout` plugin's amendments ever emptied the resolved rail — reachable because `ProtectedItemsKeys` was empty and `hide` was accepted on every Items key. | `slotSpec` gained `allowHide`/`allowIcon`/`allowGroup` capability flags; `itemsSpec` sets none of them, so `hide` on any Items key is refused at parse time — the empty-rail path this bug needed can no longer occur through any valid amendment. A defensive `len(sections) == 0` guard was also added to the handler (renders `common.error.server`) as belt-and-suspenders, since the old code indexed a statically-non-empty package var and the new one must never assume that going forward. |
| 2 | **Blocker** | The Items slot shipped `hide` with **no findability/restore surface** — contradicts ADR-0088 Decision D ("a hide mechanism without this surface is not shippable") outright; a merchant's only way back would be uninstalling the plugin. | Same fix as #1: `hide` refused at parse time on `itemsSpec` until a restore surface exists. `plugins/layout-salon`'s Items amendment only ever relabelled/reordered, so nothing the shipped demo needs was lost. |
| 3 | Medium | Two reads of the now-flat `LayoutAmendments` pool in `menu_layout_settings_page.go` (`hiddenMenuRows`, the restore/rehide POST handler) had no slot filter — benign today only because `CoreMenu` and `CoreItems` share no key strings. | Both loops gained `if a.Slot != uislot.MenuSlot { continue }`, mirroring `BuildMenuAmendments`. |
| 4 | Medium | `scripts/ci/guard-plugin-menu-read.sh`'s own doc comment says a new field reassigned inside `Reload`'s critical section must be added to its pattern — `Deps.ItemsAmendments` and `BuildItemsAmendments` were not. | Guard pattern widened (`ItemsAmendments\b`, `Build(Menu\|Items)Amendments\(`); its regression test (`guard-plugin-menu-read_test.sh`) got matching new fixtures for both. |
| 5 | Medium | `group` on an Items-slot amendment was accepted, drew no heading (the template has none), but `uislot.Resolve`'s grouping pass still physically reorders same-group rows — a **silent, unexplained reorder**, not a harmless no-op. `icon` was flagged too (a true no-op, lower stakes). Reviewer's explicit recommendation: refuse both now, not defer — permissive-now/strict-later is the one direction that isn't backward-compatible once a third-party plugin ships one. | Folded into the same `allowIcon`/`allowGroup` capability-flag fix as #1/#2. |
| 6 | Medium | `web/help/{en,de,tr}/menu.md`'s "Tiles a layout plugin has hidden" section states a `layout` plugin "only changes what the Menu shows" — now false, and I'd wrongly concluded (before review) that no help topic covered this. | Corrected in all 5 shipped locales (en/de/fa/ar/tr — the reviewer found en/de/tr; ar/fa carried the identical claim on a second grep pass). EN gained a full clarifying sentence about the Items screen; de/fa/ar/tr had the narrower fix of removing the now-false absolute clause only (verbatim retranslation of the new EN clause needs the self-hosted NAS translation model, unreachable from this cloud sandbox — same constraint several other PRs merged today hit; each locale is independently accurate as edited, just not word-for-word parity with the new EN sentence — a real, flagged gap, not silently dropped). `guard-help-drift.sh`/`guard-help-topics.sh` both stay green. |
| 7 | Medium | `reference/plugin-manifest.md` (this repo) documented only the `menu` slot for plugin authors — no mention of `items`/`CoreItems`, and its `hide` row's "restores it under Settings → Hidden menu tiles" promise is false for the Items slot. | Added a full "The `items` slot — narrower capability set" section with its own example and an explicit statement of what's refused and why. |
| 8 | Low | Stale doc comment on `plugins.Manager.LayoutAmendments` still said "Menu-slot amendments." | Updated to describe the flat, slot-filtered pool. |
| 9 | Low | The Menu-slot refusal message for an unknown key changed wording (`"...not a core menu destination"` → `"...not a core menu-slot destination"`) as a side effect of the `parseAmendment` generalization — otherwise the refactor was verified line-for-line faithful against every pre-existing refusal shape. | Accepted as-is; noted here rather than reverted, since no test pins the literal old string and the new wording is arguably clearer. |
| 10 | Low | `ParseAmendmentsJSON`'s error for a genuinely unsupported slot name (neither `menu` nor `items`) under-reported the supported set (fell through to `ParseMenuAmendments`'s own message, which only knows about itself). | Dispatcher now refuses an unrecognized slot directly, naming both supported slots. |
| 11 | Low | The new end-to-end test's `paths.Init`/cleanup didn't match this repo's own established pattern (`sync_assets_test.go`): wrong restore value (`""` instead of the prior `paths.DataDir()`), and `paths.Init` ran after `newMenuPageTestDeps` instead of before (relevant now that that helper does a `paths.Plugins()` read via the `SetLocalizer` fix below). | Reordered and fixed to match the established pattern. |
| 12 | Nit | `itemsnav.Resolve` now allocates a 5-element slice per render on the zero-plugin path (`uislot.Resolve`'s own Decision I zero-allocation guarantee is intact; the wrapper doesn't inherit it). | Noted here, not fixed — negligible on real hardware, and Decision I's own falsifiable-measurement bar is about the `uislot` primitive itself, not every caller. |

**Reviewer's other explicit conclusions, stated for the record rather than
re-derived:** `CoreItems`' five rows were hand-diffed against pre-change
`itemsnav.Sections` and are byte-identical (key/href/label/subtitle/order);
`FindConflict`'s slot-scoping is correct in production (every `Amendment`
reaching it is stamped by `parseAmendment`, no zero-value-`Slot` path
exists outside tests); the `pm.SetLocalizer(i18n)` addition to the shared
`newMenuPageTestDeps` test helper is a true no-op for all 38 existing
users (verified against `NewI18n`/`NewI18nFS`'s actual overlay
initialization, not just "tests still pass"); nothing in the diff touches
`internal/money` or `internal/pos`; no real client/shop name or
credential-shaped literal anywhere in the diff; the `ar/sell.png` /
`en/sell.png` screenshot deltas across the two `make docs-shots` runs in
this cycle are sub-pixel antialiasing noise (measured directly: 17 of
614,400 pixels, max channel delta 28, same dimensions/IDAT count), not a
real rendering change — `/sell` isn't touched by this diff at all.

## Deferred, explicitly (not silently dropped)

- **A findability/restore surface for the Items slot** (the "Settings →
  Hidden … rows" page Decision D would otherwise require) is genuinely
  future work — this card ships relabel/reorder only, with `hide` refused
  at the schema level until that surface exists. Worth a Backlog card if
  a real vertical needs to hide an Items row rather than just rename one.
- **`icon`/`group` on the Items slot** are refused, not merely
  undocumented — `items_rail.html` draws neither today; widening this
  later (once the template grows the capability) is backward-compatible,
  narrowing it after a third-party plugin ships one would not be.
- **de/fa/ar/tr `menu.md`'s new EN clarifying sentence has no translated
  counterpart yet** — each locale is independently accurate (the false
  absolute claim was removed, not left standing), but doesn't carry the
  new sentence explaining the Items-screen behavior. Needs the self-hosted
  NAS translation model, unreachable from this cloud sandbox — same
  constraint several other PRs merged today (universal-till#982, #1012)
  hit and flagged the same way.

## Verdict

findings from the independent review are either fixed (blockers 1-2,
mediums 3-7) or explicitly accepted/deferred with a stated reason (lows
9-10 partially fixed, 11 fixed, 12 accepted; the two translation/restore-
surface gaps above).
