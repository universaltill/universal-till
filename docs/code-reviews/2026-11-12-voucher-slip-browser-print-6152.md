# Review: gift voucher slips print through the browser when there is no receipt printer (ut-docs#6152)

**Change.** A till with no receipt printer can now print gift voucher slips through the browser's print dialog.
- **Voucher page (R1).** `POST /vouchers/{id}/print-slip` used to answer 409 "Set up a receipt printer" when none was configured. It now answers 200 with `X-UT-Response: print-slip`, a status line ("Print dialog opened for this slip.", neutral `tag`, no ✓) and an out-of-band slip fragment that swaps into `#voucher-slip-print`. The form's `data-after-request="ut-response:print-slip print"` (new `ut-response:<value>` guard in `web/public/inline-actions.js`) calls `window.print()` once, only on that header. The fragment's print CSS hides everything but the slip (`:has()` rules, each in its own `@media` block so an engine without `:has()` still prints the slip). The attempt is audited `voucher/<id>/slip_printed {ok:true, via:"browser"}` only after the slip has rendered. The page shows a hint above the button, plus the link to Settings → Receipt printer, when no printer is set up.
- **Sale receipt (R2).** With `printer.voucher_slip` on and no printer mode, `/api/pos/tender` appends one print-only `.voucher-slip-sheet` per issued or topped-up voucher after the receipt. Each sheet sits on its own page, uses the printed receipt's language (`receiptPrintLocale`, the #4730 rule) and RTL `dir`, and has no "Reprinted" note. If rendering fails, the slips are left out and the receipt is unaffected.
- New `internal/pages/voucher_slip_browser.go` and `web/ui/partials/voucher_slip_paper.html` (html/template, pre-translated strings, logical CSS, black on white). `vouchers.print_slip.no_printer` is removed from `en.json` and `en.meta.json`. Two new keys have meta entries. The help topics `vouchers.md` and `printing.md` are updated, and the README voucher line is updated.

**Pipeline.** Dev: Sonnet. Tester: separate agent. It ran a mutation check for each new test (every mutation went red), 38/38 Playwright tests passed, and it drove two throwaway tills (windowed and `UT_KIOSK=1`) plus a fake TCP printer, with real Chromium `page.pdf()` output inspected page by page. Reviewer: independent, different model (Opus 5.5).

## Findings
| # | Sev | Finding | Outcome |
|---|---|---|---|
| D1 | medium | **Fixed.** The R2 slip sheets live inside `#basket.receipt-view`, whose on-screen card frame (`app.css` `.pos-container > .basket`: border, `--radius-lg`, padding, `--surface`, shadow) was repeated on every slip page. In a dark theme with background graphics on, they printed as navy sheets. | `voucher_slips_receipt`'s `@media print` now drops the frame on `.pos-container` and `.pos-container > .basket.receipt-view` (border, radius, shadow, padding and margin set to 0, background `#fff`) and sets `html,body` to `#fff`. The rule ships only when slips are rendered, so receipts without slips print exactly as before. The receipt keeps its own `.receipt-card` frame. A new assertion in `receipt-voucher-slips-browser-6152.spec.ts` checks under `emulateMedia({media:'print'})` that `#basket` has 0 border, 0 radius, 0 padding and a white background. Revert-checked: with the rule removed the spec fails (`"border": "1px 1px"`), and with the rule restored it passes. |
| D2 | low | At 360px the Settings link in the hint is `inline-block; line-height:44px`, which makes the hint's last line 44px tall. That leaves an uneven gap, but nothing clips. | Accepted. This is a UX nit, and the 44px hit area is intentional (A1). |
| R1 | low | After one browser press, the slip fragment and its print `<style>` stay in the page. A later Ctrl+P on the same voucher page prints only the slip, not the page. | Accepted. The voucher page is not a document anyone prints, and the slip is the expected output there. A navigation clears it. |
| R2 | low | `browserVoucherSlipFor` reuses `voucherSlipFor`, which also rasterises the receipt logo (a file read plus a raster) that the browser slip discards. | Accepted. The cost is one manager press, not a hot path. Reusing the builder keeps the content identical to the paper slip. |
| I1 | info | Handler order: the auth gate (403), not-found, the not-printable check (409), then `printVoucherSlipIn`. That function refuses on the ADR-0124 shadow/customer-documents gate **before** it checks for a printer, so a suppressed market gets 451 and never a browser slip. The audit row is written only after a successful render. If rendering fails, the result is 500 with no audit row. | Correct. |
| I2 | info | Escaping: all slip text is `html/template` data. `barcode128svg` escapes the code in `aria-label` and builds rects from module bits only. The `<style>` bodies are template text, not data. The R2 HTML is appended to `receiptHTML` from an html/template execution. No XSS path. | No change. |
| I3 | info | i18n/RTL/rules: no hardcoded user-facing strings (the slip strings are translated in Go; the JS guard takes no text). The deleted key has no references left (`grep` is empty). CSS uses only logical properties. There is no `showModal` or `confirm`, no SQL outside `internal/data`, and no file writes or cwd-relative paths in the change. The browser path needs no network, so it works offline. Self-order checkout does not reach the slip code. | No change. |
