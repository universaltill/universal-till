# Review — theme becomes per-till, never admin-synced (ut-docs#2783)

- **Author:** Opus 5.5 (Dev). **Reviewer:** Sonnet 5, fresh context, one round. Card complexity:medium.
- **Origin:** product owner report on Pi5-1 (an additional till, WebKitGTK) — changing the theme "froze" the screen. Root cause: `theme` was not in `data.PerTillSettingPrefixes`, so it was shop-wide/admin-synced; the replica's local pick survived only until the next admin pull (main till's admin state moved every ~2 min in the field journal), which rewrote it, and the open page's `/ui/theme-sync` poll then swapped the stylesheet back. Product owner decided (2026-09-25, comment on the issue): the theme is per station — option (b), never admin-synced; per-cashier themes are a separate card.

## What shipped
1. **Theme is per-till at both ends.** New `data.ThemeSettingsKey = "theme"` added to `PerTillSettingPrefixes`: `DumpAdmin` never sends it (source), `ApplyAdmin` skips it via `perTillSetting` in the same defense-in-depth branch as the marketplace-identity keys (sink, protects against a pre-fix main till that still sends it). `TestThemeSettingsKeyMatchesCommon` keeps `common.KeyTheme` and `data.ThemeSettingsKey` from drifting apart (avoids an import cycle).
2. **Plugin-update chip on a joined till.** New `PendingUpdateStatus.MainTillURL`, published by `PublishPendingUpdates` (renamed from `SetPendingUpdates`, all 8 call sites across `httpx`, `pages`, `plugins` updated). `base.html` now shows "Updates are installed from the main till (N)" instead of an unactionable "install" chip, linking to the main till's own `/plugins` where a cross-device link is actionable (`crossdevicelinkactionable`, the existing `inventory.html`/`catalog.html` seam — reused verbatim, same `target="_blank" rel="noopener" hx-boost="false"` markup), or to this till's own `/tills` page (names the main till) on a kiosk where it isn't.
3. **i18n + manual.** `settings.theme.help_per_till` and `status.plugin_updates_from_main` added to en/ar/fa/tr (the only locales in this repo; de/es are separate language-pack repos, out of scope). `web/help/{en,de,tr,fa,ar}/{display,plugins}.md` updated to describe the new per-till behaviour and the main-till chip.

## Verified
- **Both ends enforced, not just the sink:** `TestAdminDumpApplyRoundTrip_ThemeIsPerTillAndNeverSyncs` proves the main never dumps the row *and* a replica ignores it even from a "pre-fix main" that still sends it (3 repeated applies, simulating the 30 s drift loop). Reverted the fix (dropped `ThemeSettingsKey` from the prefix list) myself: this test fails with "the main till's theme leaked into the admin dump", and the new `TestReplicaTheme_SurvivesMovingAdminPullsAndThePollNeverFlips` (end-to-end: real settings save + real admin pull + real poll against a moving main) fails with "reverted to monarch (want its own slate)". Restored the fix: both green again, diff unchanged.
- **Join snapshot still seeds a new till with the main's theme — confirmed intended.** `RedactedJoinSnapshot` is a raw whole-DB `VACUUM INTO` copy; it only redacts `bearer_hash` and the marketplace-identity settings rows, never `theme`. A freshly joined till therefore inherits the main's current theme as its own per-till starting value, matching the new help text ("A newly joined till starts with the main till's theme").
- **No other sync path.** The only generic settings-write cloud directive, `set_setting` (`cloudsync.Hooks.SetSetting`), writes straight to the receiving till's own `d.Settings` — cloud directives are per-till-addressed commands, not a shop-wide broadcast, so a cloud-issued theme change was already effectively per-device before this fix and needed no change here. `apply_design` (mentioned only in a payload-shape comment) has no till-side handler at all.
- **Chip security/UX:** `MainTillURL` is the same LAN address the replica already syncs against — no new exposure. `crossdevicelinkactionable` defaults to `selfupdate.DownloadLinkActionableNow()` (false on unix kiosk), so the kiosk WebView path never gets a `target="_blank"` link it can't act on; verified with a real e2e run.
- **Gates:** `gofmt -l .` empty, `go vet ./...` clean, `go build ./...` clean, `guard-i18n.sh`, `guard-data-access.sh`, `guard-help-topics.sh`, `guard-help-drift.sh` all pass (drift guard's only hits are pre-existing baselined entries, unrelated to `display`/`plugins`).
- **Tests:** `go test ./internal/data/...`, `./internal/pages/...`, `./internal/httpx/...`, `./internal/plugins/...` all pass. `-race`: `internal/httpx`, `internal/pages/common` (full), `internal/plugins -run PendingUpdate` and `internal/pages -run PluginUpdateCheckTick` (the concurrency-sensitive paths touched by the `PublishPendingUpdates` rename) all clean.
- **e2e:** ports 8091–8093 were free; ran `theme-sync-2343.spec.ts` (pre-existing, unrelated to this card but the closest live-browser coverage of the poll/reload behaviour this fix depends on) — both cases pass. No docs-shots run (no visual UI change beyond one help-text line and a chip's copy, already covered by the existing screenshot set's copy source).
