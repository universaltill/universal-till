# Review — ut-docs#2815: price edits revert on Save (p1 regression)

**Branch:** fix/2815-variant-price-save · **Reviewer:** Fable (independent, different model from the Opus author) · **Verdict:** safe to merge after one fix (applied)

## What shipped
Three client-side causes of "I change a price, press Save, and it goes back":
1. **On-screen keyboard inserts at the caret** (the product owner's own case on the tablet, v0.24.0, de). Tapping a filled "5.00" and pressing 6 gave "5.006". The price `pattern` refused it, so nothing was posted, and Android WebView shows no validation bubble. `osk.js` `show()` now selects a filled numeric field on its first tap, so the first key replaces the amount; a re-tap keeps caret placement. `type=number` is excluded because `insert()` appends there.
2. **Variant rows posted the old price.** An existing variant form's hidden `name="id"` shadows `form.id`, so the major→minor copy found no form and the stale hidden price was sent. The lookup now walks `form.elements`.
3. **Decimal comma** ("5,50" from a German keyboard or the de OSK). The pattern was dot-only and `toMinor` returned 0. Fixes: `moneypatternlocal` (dot or comma), `utCurrency.parseMinor`, an `invalid` capture that shows the refusal in the dialog's notice, a server-side localized 400 for non-integer minor prices, and a "Saved" line in the variant panel.

## Verified beyond automated tests
- Drove the **tablet's own server** (192.168.1.136, v0.24.0, de, touch emulation). The server save works (5.00 → 6 stored as 600, then restored to 500). The OSK path reproduces the owner's symptom exactly: the field reads '5.006', no POST is sent, and no message is shown in the dialog.
- New e2e drives the real OSK keys: it **fails without the fix** (received "4.006") and passes with it (re-verified by the author). The reviewer independently re-verified cause 2: with the old lookup restored, 2 tests fail posting `price=200`.
