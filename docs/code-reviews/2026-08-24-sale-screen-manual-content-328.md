### Findings — fixed in this branch before merge

1. **(High) Customer-linking claim was wrong.** The draft said any loyalty
   number or phone number scanned into the barcode box would link a
   customer. `looksLikeCustomerCode` (`internal/pages/pos_api.go`) only
   recognizes codes starting `CUST`, `LOY-`, or `LOY`+digit — a bare phone
   number or loyalty number falls through to "Item not found" instead.
   **Fixed**: `sell.md`'s "Linking a customer to a sale" section now names
   the actual recognized code shapes and the resulting failure mode.
2. **(Medium) Offline-toggle scope was wrong.** The draft said the
   offline-override checkbox marks "this one sale" as offline. It's
   actually a sticky setting persisted to `localStorage`
   (`web/public/app.js`) that stays on across sales and till restarts until
   manually unticked. **Fixed**: reworded, with an explicit note to switch
   it back off after the outage.
3. **(Medium) Dangling cross-reference.** `sell.md` pointed to `payments.md`
   for the offline toggle; `payments.md` never mentions it (the toggle
   actually lives on the sale screen, not the payments panel). **Fixed**:
   describes the toggle in place in `sell.md` instead of cross-referencing
   a section that doesn't exist.
4. **(Medium) Missing "what can go wrong" states**, against the manual's own
   required structure:
   - A per-line discount larger than the line's own value is accepted while
     building the basket but rejected at tender with a generic,
     unhelpful message. **Fixed**: added as a caution in the Discounts
     section.
   - Changing a line's quantity after setting its discount silently clears
     the discount to `0` (a real product-level defect — the redisplayed
     value is in major units but the handler parses it as an integer minor-
     unit value; see "Deferred" below). **Fixed**: added a "set quantity
     first, discount last" note so the manual doesn't leave the cashier to
     discover this the hard way.
   - `payments.md`'s Split section didn't cover underpayment (Complete Sale
     with pending payments still short of the total) or Fill Remaining's
     own two refusal cases. **Fixed**: added to the "What can go wrong" list.
5. **(Low) Suggestion-chip claim overclaimed.** "Same as tapping its tile"
   is wrong for a customizable item — a tile opens the modifier picker, a
   suggestion chip adds the item directly, skipping customization.
   **Fixed**: reworded with an explicit caveat.
6. **(Low) Status-chip count was wrong.** "Two small chips" undercounts —
   there are up to four (session, sync, fiscal, bug-report).
   **Fixed**: reworded to avoid a specific wrong count and cross-link the
   fiscal chip (already documented in this same file's TSE section) and the
   bug-report chip.
7. **(Low) Change-note placement.** Described as appearing "underneath" the
   pending-payment amount; it actually renders inline, in parentheses, on
   the same line. **Fixed**.
8. **(Low) "Greyed out" / tax-timing wording.** The inactive dine-in/takeaway
   button is a normal, fully-tappable secondary-styled button, not a
   disabled one — "greyed out" reads as disabled. Also clarified that the
   shown total updates immediately on toggling, not just "at the moment of
   payment". **Fixed**.

### Deferred — real product defect found, out of scope for this docs card

Editing a basket line's quantity after setting that line's discount silently
resets the discount to `0`: the discount box redisplays in major currency
units (e.g. `0.30`), the quantity input's `hx-include="closest tr"` re-posts
that same value as `discount`, and the handler's `strconv.ParseInt` (expecting
minor units) fails and falls back to zero with no error surfaced. This is a
genuine bug in `internal/pages/pos_api.go`'s line-update handler, not a
documentation gap — **filed as ut-docs#971** rather than fixed here, since
fixing it means touching `.go`/`.html` files outside this card's scope.
