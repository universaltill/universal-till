# Review: Android WebView print bridge (ut-docs#6153)

**Change.** In the Android app, `window.print()` did nothing: Android's WebView has no print dialog of its own. So the receipt's Print / Retry print browser fallback and the #6152 voucher-slip fallback printed nothing on an Android till, while the slip fallback still logged `slip_printed {via: browser}`. Now the till asks the Android shell to open the system print dialog for the current page.

- **`android/.../MainActivity.kt`:**
  - `KioskBridge` (`window.AndroidKiosk`) gains `@JavascriptInterface fun print(): Boolean`. It takes no argument, so nothing the page sends reaches a URL, a file or the job name. It returns true when a dialog was asked for, and false when printing is unavailable or a dialog is already open.
  - A double tap opens one dialog: an `AtomicLong` in-flight slot is claimed with CAS on the bridge thread.
  - `startPrint(claimed)` runs on the UI thread: `PrintManager.print(jobName, ReleasingPrintAdapter(webView.createPrintDocumentAdapter(jobName)), null)`. The wrapping adapter releases the slot in `onFinish`.
  - The bridge refuses while the kiosk is pinned (`kioskPinned` or `lockTaskModeState != NONE`) and never unpins. The print spooler is not added to the lock-task allowlist, because its "Add printer" path leads to Settings and the Play Store.
- **`PrintLogic.kt` + `PrintLogicTest.kt`:** pure logic for the job name (control characters stripped, capped at 64 characters, surrogate-safe), the in-flight window (it clears itself after 120 s) and the can-print decision.
- **`web/public/inline-actions.js`:** a local `printPage()`, also published as `UT.print`, replaces all five `window.print()` calls (the `print` action, `receipt-ask-print` ×2, `receipt-print` ×2). It uses the bridge when `AndroidKiosk.print` exists and `window.print()` otherwise. If the bridge throws or refuses, it never falls through to `window.print()`. The 451 refusal still prints nothing. `web/ui/partials/receipt.html`: comments only.
- **Docs:** `web/help/en/printing.md` and `web/help/en/vouchers.md` no longer say the Android app opens no print dialog (English only, ADR-0160). `android/README.md` has a Printing section. `web/help/img/manifest.json` was regenerated by `make docs-shots`; every PNG came out byte-identical, so only the hashes changed.
- **`e2e/tests/android-print-bridge-6153.spec.ts`:** covers receipt Print, the 451 case, receipt-ask Print, the voucher-slip fallback (one audit row per tap) and a bridge that refuses, each with and without a stubbed bridge.
- No Go change, no new i18n key, no ADR (ADR-0023's bridge pattern covers it). ut-docs: no change.

**Pipeline.** BA ran on the session model, Architect on Opus 5.5, Dev on Sonnet, Tester on the session model, and the Reviewer was a separate agent on Opus 5.5.

Pre-flight: help topic updated (`printing`, `vouchers`) + `make docs-shots` run (manifest only, guard green); `reference/` n/a (no page describes Android printing); README n/a (no Android printing claim); `en.json` n/a (no new key); platform claim n/a (no new platform); review record: this file.

## Findings
| # | Sev | Finding | Outcome |
|---|---|---|---|
| F1 | low | `kioskPinned` was read on the JavaBridge thread without `@Volatile`. If screen pinning was declined, it is the only thing that refuses printing on a self-order page, so a stale read could let a print dialog open there. | **Fixed:** `@Volatile`. |
| F2 | low | `onFinish` always cleared the in-flight slot, so a late `onFinish` after the 120 s window could clear a newer dialog's claim. | **Fixed:** `startPrint(claimed)` releases with `compareAndSet(claimed, 0L)` on every path. |
| F3 | info | A refused bridge call gives the cashier no feedback. This is not a regression: Android printed nothing before. | Accepted. |
| F4 | info | `manifest.json` says not to edit it by hand. | It was produced by `make docs-shots` (132 shots passed), not by hand. |
| T1 (Tester) | defect | `guard-docs-shots.sh` failed: the surface hash and the `en/vouchers` topic had changed. | **Fixed:** `make docs-shots`; guard exits 0. |

## Verification
- **TDD:** the spec was written first and failed on the bridge cases. The Tester and, separately, the Reviewer reverted only `inline-actions.js` to `origin/main`: 5 bridge cases failed, and the plain-browser and 451 cases still passed. After restoring the file, everything passed. The Tester also made the 451 path print: all six "451 prints nothing" cases failed.
- **e2e:** the new spec plus the 6152, 4714 and 6167 print specs: 27 passed (Tester), 24 passed (Reviewer's run). After rebasing onto #6155 (print page margins), the new spec plus the 6152, 6155, 4714 and 6167 print specs: 29 passed; `make docs-shots` re-run, guard green.
- **Kotlin:** `PrintLogicTest` 14/14 in a throwaway Kotlin 2.0.21 / JUnit 4.13.2 JVM project. Three deliberate breaks each made tests fail. `MainActivity.kt` could not be compiled here because there is no Android SDK; it was checked by reading (adapter override signatures, `lockTaskModeState` API 23 vs minSdk 24). CI's `android-ci` Gradle build and unit tests are the compile proof.
- **Driven run:** the real till in Chromium at 1280×800: the receipt screen looks the same with and without a stubbed bridge. Print with no printer (502) called `window.print` once without the bridge and only the bridge with it. A throwing bridge never fell through.
- **Guards:** docs-shots, i18n, help-topics, help-drift, rtl-logical-css, fixed-dates, no-native-confirm, mail-addresses and core-neutral, plus 28 other build-job guards covering `web/`, `android/` and `e2e/`: all exit 0.

## Verdict
Ship. **Deferred:** a real device or emulator check of the dialog and of the refusal while pinned. No device is reachable from a cloud lane; this is noted on ut-docs#6153 for the local lane.
