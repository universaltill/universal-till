# Review: msstore-submit non-2xx diagnostics (2026-11-27)

Pre-flight: shell-only change; no Go, UI, i18n, data access or help topic touched.

## What shipped (uncommitted diff)
`scripts/ci/msstore-submit.sh` and `msstore-submit_test.sh`: on any non-2xx Store API answer print the HTTP code,
a sanitised capped error body (whitelisted JSON fields) and the token's non-secret claims decoded locally.

## Verification
- shellcheck clean on macOS (0.x); on Ubuntu 24.04 only SC2015 info at pre-existing line 66.
- msstore-submit_test, guard-store-private (+ _test), promote-release-workflow_test: all pass (macOS bash 5.3 / jq 1.8.2;
  msstore-submit_test also on Ubuntu 24.04 amd64, jq 1.7, GNU base64 9.4).
- Adversarial: JWT in body, JWT split over lines, opaque token echo, `::error::`/`::add-mask::` (single and multi-line, CRLF),
  long bodies, non-UTF8, NUL, unicode separators, odd claim types, base64url padding 0-3, exp overflow/string/object.
- Write path (PUT/POST), opening-file check, EXPECT_SHA256 and blob re-hash are outside the diff and unchanged.
  Store-private guard unchanged and green.

## Findings
1. (medium) Token scrub is shape-based (`eyJ...`) only. A JWT split across lines leaks its signature segment; an echoed
   non-JWT/opaque value is printed. Mitigated in CI by `::add-mask::` of the exact token, but not for split forms.
   Suggest also scrubbing the exact token (and its signature segment) read from the token file.
2. (low) Empty-whitelist fallback is dead: jq prints "\n", `clean` makes it a space, so `[ -n "$out" ]` is true and the
   "(JSON body without a known error field)" message never appears (`{"x":1}` prints a blank line).
3. (low) `exp` above ~1e18 makes `strftime` error and the whole claims line is empty; a missing/non-numeric exp prints
   a misleading `1970-01-01`.
4. (low) The claims line (tid, appid, oid) is printed on every run, including green dry runs, and the repo is public, so
   Actions logs are world-readable. These are identifiers, not secrets; owner decision whether to print only on failure.
5. (nit) On macOS a non-UTF8 non-JSON body makes `tr` fail ("Illegal byte sequence") and the body is dropped; Linux fine.
6. (nit) Claims are printed twice on a failing first probe. `bash -x` still shows the token (pre-existing line 100).

## Verdict
No leak of the token, its signature (whole-token forms), header file or Authorization header found in the tested paths;
seller line prints only the validated numeric seller id and alnum product id. Findings reported, none fixed here.
