  verifying the ticket's own no-op-override criterion (see below).

## What the independent review found

One **blocker**, four **should-fix**, three **nits**. Full findings are in
the review transcript (not reproduced here in full); the material ones:

1. **BLOCKER — the no-op-override acceptance criterion was mis-scoped, and
   the case it actually names was genuinely broken.** The ticket's
   criterion 2 is about a hand-created 19/19 (or 7/7) *tax code*, not the
   plugin's `takeaway_rate_overrides` JSON — its own wording ("code
   churn", "export/import round-trip") is core-pipeline vocabulary
   (ut-docs#512/#535/#536). The reviewer ran the criterion as actually
   specified and reproduced real churn: a hand-created equal-pair tax code
   (via `POST /api/catalog/tax-codes`) stored an *explicit*
   `takeaway_rate_basis_points`, which `FindOrCreateTaxCode`'s
   `(rate, takeaway)` lookup could never match against a later import's
   canonicalized `(rate, nil)` query — silently creating a duplicate code
   and migrating every subsequently-imported item onto it, abandoning the
   merchant's own code. Pre-existing bug, not introduced by this card; the
   ticket exists precisely because "nothing proves it is covered," and a
   real test as specified would have (and did) find it.

   **Fix:** canonicalize an equal-pair `(rate, takeawayRate)` to "no
   override" (`nil`) at `parseTaxCodeForm` — the one place a human
   hand-creates or edits a tax code — exactly mirroring the
   canonicalization `import_page.go`'s CSV-import path already applies at
   parse time. Added `TestTaxCodesAPI_Create_EqualPairCanonicalizesToNoOverride`
   (`tax_codes_page_test.go`, covering both create and update) and
   `TestHandCreatedEqualPairTaxCode_MatchesFreshImportNoChurn`
   (`import_page_test.go`, the full downstream consequence: a hand-created
   code plus a fresh CSV import of the same pair land on the SAME tax
   code, no duplicate). Also fixed the one existing test the
   canonicalization broke, `TestTaxCodesAPI_Create_AcceptsExactly100`,
   which had incidentally used an equal pair for an unrelated boundary
   assertion (rate=100, takeaway=100 → changed takeaway to 50, a value not
   equal to rate=100, preserving that test's actual intent).

2. **SHOULD-FIX — the original modifier test passed with the modifier
   deleted entirely.** `PriceDeltaMinor: 0` meant the modifier contributed
   nothing to any assertion regardless of whether it inherited the
   parent's rate or was ignored outright. **Fix:** re-priced the modifier
   (`PriceDeltaMinor: 100`, with round numbers chosen so the arithmetic
   stays exact) so the assertion actually distinguishes "inherits the
   parent's rate" from "changed nothing." Added a structural guard via
   `reflect` over `data.SelectedModifier`'s field set, asserted first, so
   a future rate/tax field addition fails loudly instead of leaving the
   test silently checking nothing.

3. **SHOULD-FIX — the refactor silently dropped the dine-in short-circuit.**
   `taxrate.Resolve(orderType, taxCodeID, overridesJSON string)` took
   `overridesJSON` as a plain string, evaluated eagerly at the call site —
   `setting("takeaway_rate_overrides")` — even on the dine-in path, where
   the original inline handler never touched the settings JSON at all.
   Not a correctness bug (malformed JSON was still silently ignored on
   dine-in, since `Resolve` returned before parsing), but a real added
   host round-trip (`settings_get` → SQLite read) on every dine-in line —
   the common case, most receipts — that the removed code never paid.
   **Fix:** changed the parameter to `overridesJSON func() string`, so
   `main.go` passes a closure and it's called only on the takeaway path.
   `TestResolve_DineInNeverConsultsOverrides` now uses a tripwire closure
   that calls `t.Fatal` if invoked at all, rather than only checking the
   observable result.

4. **SHOULD-FIX — the "no-op override stability" test did no actual
   round-trip.** The four JSON variants differed only in whitespace/key
   order, both of which `encoding/json` is definitionally insensitive to
   — nothing was parsed and re-marshaled. **Fix:**
   `TestResolve_NoOpOverrideStableAcrossReserialization` now parses each
   variant, re-marshals it with `encoding/json`, and resolves against the
   re-marshaled bytes — an actual round-trip.

5. **SHOULD-FIX — no committed wasm-level test for `tax.rate.ask`.**
   `Resolve(orderType, taxCodeID string, ...)` takes two same-typed
   strings; a swapped argument order at the `main.go` call site would pass
   every test in both packages while being wrong for every real till.
   **Fix:** added `TestTaxRateAsk_TakeawayOverrideAnswersReducedRate` and
   `TestTaxRateAsk_DineInAnswersNothing` to `src/wasmrun`, driving the real
   compiled `bin/plugin.wasm` through wazero.

6. **SHOULD-FIX — README reinforced a wasm-coverage claim contradicted by
   the code.** Fixed the wording in `README.md` and the `src/wasmrun`
   package doc comment to reflect that `tax.rate.ask` now has its own
   committed wasm-level cases, not just an ad-hoc historical run.

7. **NIT — `ParseOverrides("null")` returned a nil map.** Fixed: an
   unmarshal of JSON `null` is normalized back to a non-nil empty map, and
   `TestParseOverrides_Empty` now covers `"null"` explicitly.

Two nits not separately fixed: no code-review record existed yet at
review time (this file is that fix) and the matrix test's
`wantEffectiveBP` column re-derives core's own fallback rule rather than
calling it directly — noted as documentation of the matrix, not a defect
in what it tests.

## Scope note

No behavior change in core beyond the equal-pair canonicalization fix
(finding 1) and the new tests — the actual (product class x consumption
mode) VAT rule lives entirely in `ut-plugin-tax-de`, per ADR-0050 /
criterion 6. The canonicalization fix touches `parseTaxCodeForm` only
(shared by both the create and update HTTP handlers); no schema change,
no new SQL, no new user-facing string.
