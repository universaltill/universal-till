# 2026-07-26 — Android native shell, Phase 2 (ADR-0023, spec 013)

## Context
Phase 1 (`internal/app.Run` + the `mobile` Go package, merged as PR #60)
built the Go-side groundwork `gomobile bind` wraps. Farshid: "install it
on my machine" (the Android SDK), then, going to sleep: "go to the end
and finish it." This is that: the actual native Android app — a real
Gradle project, a real APK, built and run end-to-end on a real emulator,
not just scaffolding.

## Design
- `app/libs/unitill-mobile.aar` — generated by a Gradle `Exec` task
  (`generateAar`) shelling out to `gomobile bind -target=android
  ./mobile`, wired into `preBuild`. Never committed (a ~90MB build
  artifact); the task deliberately never treats itself as up-to-date
  (see Independent review §1 below for why).
- `TillService` — a foreground `Service` owning the embedded server's
  lifecycle independently of any Activity. Exposes `address`/
  `startError` plus a listener mechanism so a late-binding Activity
  (e.g. after process death + restart) learns an already-resolved
  result instead of waiting again.
- `MainActivity` — binds to `TillService`, points a `WebView` at
  whatever address it reports, requests `POST_NOTIFICATIONS` at
  runtime (API 33+, best-effort), wires the system back button to
  `WebView.goBack()`.
- `network_security_config.xml` — cleartext HTTP allowed **only** for
  the literal `127.0.0.1`, not a blanket exemption.
- `android:configChanges` on `MainActivity` — rotation doesn't destroy/
  recreate the Activity (or its WebView) at all; combined with
  `TillService` surviving independently either way, a rotation is a
  true no-op for the running till.

## Independent review
Sonnet-model review, read-based (no Android SDK on the reviewer's
environment) but grounded directly in the Go side it binds against
(`mobile/mobile.go`, `internal/app/app.go`, `internal/db/db.go`,
`internal/server/server.go`), explicitly asked to think adversarially
about Android lifecycle edge cases a single manual click-through
session is least likely to exercise.

**Confirmed correct, not just eyeballed**: the listener registration's
lock-ordering (write-before-lock in the worker thread, read-after-lock
in `addListener`) genuinely guarantees no listener is ever silently
missed — traced the actual happens-before relationship, not assumed;
`MainActivity`'s bind/unbind across rapid rotation has no stale-reference
window (Android's own `ServiceDispatcher.mForgotten` flag already
handles the "callback fires after unbind" race, a well-known platform
mechanism, not a gap in this code); `foregroundServiceType="specialUse"`
+ its required property are correctly paired and safe across the full
minSdk 24–36 range (unrecognized service-type bits are ignored on older
platforms, not rejected); `network_security_config.xml`'s scope exactly
matches what `mobile.Start` actually returns, no mismatch.

**Four real, worth-fixing findings, all fixed:**

1. **`generateAar`'s Gradle `inputs.dir` tracking was incomplete —
   could silently package a stale `.aar`.** The task only tracked
   `mobile/` and `internal/app/` as inputs, but `internal/app.Run`
   transitively imports a much larger fan-out (`config`, `db`, `pages`,
   `plugins`, `server`, ...) that Gradle's file-based staleness
   checking can't express without literally tracking Go's whole import
   graph. Editing any of those untracked packages would leave the task
   `UP-TO-DATE` and ship old Go code in the APK — directly contradicting
   the "always regenerated from source" claim the task's own comment
   made. Fixed: `outputs.upToDateWhen { false }` — always reruns
   (`gomobile bind` takes well under a minute; correctness over
   marginal speed for a task whose whole job is being the source of
   truth). Verified: the rebuild after this fix shows `generateAar`
   actually executing, not `UP-TO-DATE`.
2. **Missing `webView.destroy()` — a standard, well-documented Android
   WebView leak.** `onDestroy()` never released the `WebView`; every
   Activity recreation (or finish) leaked the instance. Fixed with
   detach-then-destroy (destroying an attached WebView is documented
   as unsafe). Verified: real back-navigation exit produces no crash
   and no `FATAL`/`AndroidRuntime` log entry.
3. **`TillService.onDestroy()`'s fully detached, unawaited
   `Mobile.stop()` routinely discarded a real graceful-shutdown
   window.** `internal/server.Start` allows up to a 5s drain before
   `internal/app.Run`'s deferred `database.Close()` runs; a fully
   fire-and-forget thread raced that against however long Android
   grants after `onDestroy()` returns before reclaiming the process —
   for an ordinary user-driven stop (not an OOM kill, which bypasses
   `onDestroy` regardless of what this code does), that's real,
   avoidable data loss on the margin. Fixed: bounded synchronous join
   (3s cap) — briefly blocks the main thread during shutdown only, not
   during normal operation, which the review characterized as an
   acceptable, well-precedented tradeoff.
4. **The reload-avoidance check in `MainActivity`'s listener callback
   was permanently inert.** Its comment claimed it avoided discarding
   in-page state across rotation, but without `configChanges`, the
   Activity (and therefore the `WebView`) was unconditionally destroyed
   and recreated on every rotation regardless — so the check's
   `webView.url` was always `null`, always triggering a reload anyway,
   achieving nothing the comment claimed. Fixed at the root cause:
   added `android:configChanges` so rotation doesn't recreate the
   Activity at all, which is what makes the WebView (and this check)
   actually persist and mean something. Verified: post-fix, a real
   rotation produces no new "listening on" logcat line at all (not just
   an unchanged one) — confirming the Activity itself isn't recreated,
   a strictly stronger result than Phase 2's first verification pass.

**Also independently confirmed as genuinely safe, not just declared
safe**: `TillService`'s `android:exported="false"` — tested directly
with `adb shell am stopservice`, which the OS itself rejected
("Permission Denial: ... not exported"), proving external processes
really cannot reach the service, not just that the manifest claims so.

## Verification
Two full live passes against real built APKs on a real Android emulator
(API 36, arm64) — before and after the 4 fixes above, not just once:

- Real APK installs and launches; embedded Go server genuinely boots
  (`GoLog: Universal Till POS starting...`), binds a real loopback
  port; the real setup wizard (language picker, ar/en/fa/tr) renders in
  the WebView.
- Real interactivity: taps advance the wizard (language → country
  step) — genuine touch → WebView → server round trips.
- Rotation: same process PID, same listening port, before/after (first
  pass); after the `configChanges` fix, no new Activity `onCreate`/
  server restart at all (second pass) — the stronger, correct result.
- Clean exit: back-navigation twice produces no crash, `TillService`
  correctly keeps running afterward (by design).
- Real launcher icon (converted from `web/public/assets/logo/ut-logo.svg`
  via `rsvg-convert`) renders correctly on the home screen/app drawer.
- `generateAar` confirmed re-executing (not `UP-TO-DATE`) on the
  post-fix rebuild.

## Explicitly not done
Release signing/distribution, physical hardware integrations (the
`runtime:"go"` process-spawning plugin type doesn't port to mobile —
ADR-0023 §2), an in-app "stop the till" affordance, and CI wiring for
this app (Android SDK/NDK footprint not yet scoped for CI) — all
documented in `android/README.md`'s "Not yet done" section, not
silently skipped.
