# Review: joining a cloud shop (ut-docs#5098)

Branch `fix/5098-join-flow`. Independent review by a fresh-context opus agent
(read-only), findings below.

Owner test 2026-10-26 (fresh install, joined a my. shop as its main till).

## Root causes

1. **Shop type asked again.** Not a till bug. The till skips the step when the
   pair answer carries `store.shop_type` (ADR-0171, `cloudShopView`,
   `web/ui/pages/setup.html` `cloudShopType`). ut-cloud answers
   `StoreAccount.shop_type`, else the type the shop's till last reported
   (`merchantauth.mirroredShopType`), and that lookup ignores a removed
   (tombstoned) till. The owner had pressed Remove on the old till, so a
   till-born shop answered `""` and the wizard asked. Needs a ut-cloud
   decision (keep the last mirrored type); not changed here.
2. **Import welcome after the join.** The wizard redirected to
   `/import?welcome=1&syncing=1` and `import.html` always rendered the
   empty-shop welcome (plus a chip). Nothing looked at the catalogue or at
   the pull. Fixed: `join_sync.go`.
3. **No plugins.** No code path installs a tax plugin for any country but a
   prompted German tile (`countryTaxLocale` is DE only; `basePluginsForCountry`
   is language-only; a GB shop's language is bundled, so nothing to install).
   ADR-0172 (auto-install the country's tax plugin, owner decision on
   ut-docs#4837) is still Proposed and unbuilt, and the live `tax-uk` 1.3.0
   listing is ineligible under its own section 2 (`markets: []`, a `net:`
   permission). Not changed: needs the owner to accept ADR-0172 and decide the
   plugin release (markets GB, MTD export split). The install path
   (marketplace installer, Ed25519 manifest verifier) is untouched.
4. **Refused catalogue row.** The feed serves a row at its latest version, so
   an `item_barcode` last written at v9 can name an item last edited at a
   higher version. The barcode applied first, was refused ("has not reached
   this till"), the cursor moved past it and only a later edit of the barcode
   would resend it: stuck. The existing in-group ordering (ut-docs#4522) only
   covers rows of one version. Fixed: such a row is deferred and applied once
   at the end of the run (`retryDeferred`); still refused and logged only if
   its parent never arrives.

Add-on (coordinator): the my. "Attention needed" list kept the first failed
pair attempt (`pair-first setup failed: the shop already has a till`) after a
later join succeeded. The Problems ring entry was unkeyed. Now keyed
(`enrol.pair_failed`) and resolved on a successful pair or commit. The disk
message is ut-docs#5099, untouched.

## Changes

- `internal/catalogpull`: `notReachedError`, `runner.deferred`,
  `retryDeferred`; a newer version of a deferred row settles the older one as
  a refusal (count and log kept, newer outcome recorded); the link is touched
  on deferral so a resync prune cannot take it.
- `internal/enroll/pair.go`: `ProblemKeyPairFailed`.
- `internal/pages/join_sync.go`, `import_page.go`, `import.html`,
  `setup_page.go`: join marker, syncing state, redirect to the sale screen,
  poll `GET /ui/join-sync` (204 while pending, then `HX-Redirect`).
  Window 3 minutes, so an offline till is never trapped.
- `internal/cloudsync/catalog_pull.go`: `first_pull_done` when a run reaches
  high_water.
- Locale keys `setup.cloud.syncing_title`, `setup.cloud.syncing_body` (en, ar,
  fa, tr); help topic `multitill` in en, de, ar, fa, tr.

## Independent review findings

Two blockers, five minors; all fixed.

1. Blocker: a deferred row was not recorded, so a last pass that never ran
   (deadline, restart) left a silent gap behind the moved cursor. Now the
   refusal is recorded at deferral and a successful apply clears it; the last
   pass is skipped on a dead context.
2. Blocker: replaying deferred rows in version order missed chains
   (barcode -> item -> category). The deferred set is now one group in
   dependency order (`orderGroup`) with repeated passes until no progress.
   Test `TestPullReferenceChainAcrossVersionsApplies_5098`.
3. The item-photo hook now fires after the last pass commits.
4. `first_pull_done` is written once, not on every tick.
5. A join time in the future (clock moved back) reads as expired
   (`TestJoinSyncClockGoingBackwardsExpires_5098`).
6. The standalone-marker test now drives the standalone final post.
7. Dead `cloudSyncing` chip branch and template variable removed.

Also fixed from CI-style checks: `GET /ui/join-sync` classified in
`demo_mode.go` (denied, like `/import`), claimed by the catalog help topic,
two i18n-meta entries, docs-shots refreshed (multitill), surface hash.

The reviewer confirmed the diff does not touch plugin install, the marketplace
verifier or key handling.

## Not fixed here (escalated)

- Shop type asked: needs a ut-cloud decision (keep the last mirrored type of a
  removed till, or store it on the shop).
- Plugins: needs the owner to accept ADR-0172 and decide the `tax-uk` release
  (markets GB, no `net:` permission); the live 1.3.0 listing is ineligible
  under ADR-0172 section 2.
- A till already holding a stuck refusal from before this fix keeps it until
  the row changes or a resync; no applier-version bump (would re-pull every
  till).
